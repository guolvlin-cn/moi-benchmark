## 四、通过的能力范围

### 4.1 分支隔离

所有仅发生在分支上的新增、修改和删除均与主分支保持隔离。两个同级分支能够维持彼此独立的状态；重复签出（Checkout）能够恢复完全相同的历史状态哈希；主分支继续演进不会改变此前创建的分支。在所有要求检查的场景中，检索结果均跟随当前签出的分支。

### 4.2 结构化差异

单一变更和混合变更均能被准确分类到 `added`、`updated` 和 `removed`，且实际别名集合与预期完全一致。五种混合形态覆盖新增/修改、新增/删除、修改/删除、新增/修改/删除，以及每类各两个变更。主分支上的独立新增会出现在 `behind_main` 中；重复读取差异也始终返回相同的预期分类。

### 4.3 追加合并

所有无冲突追加用例均通过，包括新增 1、2、3、5 条记忆，混合记忆类型，主分支独立演进，重复合并，以及合并后继续向主分支写入。重复合并返回 0 个新增项，状态哈希保持不变；合并后的状态和检索检查也全部通过。

该结果有意限定在逻辑无冲突用例中已验证的 `append` 策略，不能据此证明通用三方合并或冲突解决的正确性。

### 4.4 正向冲突检测

10 个真实分歧用例全部通过：

- 修改/修改：`4/4`；
- 分支修改/主分支删除：`3/3`；
- 分支删除/主分支修改：`3/3`。

每个冲突都能关联到预期的原始记忆，并展示预期的分支后继状态和主分支后继状态。全部 12 个冲突类用例在检查差异后都没有改变主分支。本类别没有执行合并（Merge）、应用（Apply）、选择（Pick）或其他冲突解决操作。

## 五、失败的负向对照

### 5.1 双方更新为相同内容

用例 `bdm-formal-049-same-update-1` 在分支和主分支上都将 Project Cedar 修改为 Project Maple。由于双方最终内容相同，语义预期是不存在冲突，但 API 对原始记忆返回了一个冲突：

- 分支后继内容：`Will is working on Project Maple.`
- 主分支后继内容：`Will is working on Project Maple.`

该用例仅“`conflicts` 应为空”这一条断言失败，其余 7 条必需断言均通过。

### 5.2 双方删除同一内容

用例 `bdm-formal-050-same-delete-1` 在分支和主分支上都删除了同一条 Project Harbor 记忆。语义预期是不存在未解决冲突，但 API 返回了一个冲突，其中分支侧和主分支侧均已失活且不存在后继记忆。

该用例同样仅“`conflicts` 应为空”这一条断言失败，其余 6 条必需断言均通过。

## 六、实现层原因

在本次固定的源码版本中，结构化差异先构造 `branch_mids` 和 `main_mids`，再对两者取集合交集，将同时出现在两侧的所有记忆 ID 定义为冲突，并直接根据该集合构造冲突条目。分类器没有先比较后继记忆的内容，也没有识别双方独立将同一源记忆标记为失活的情况。

该逻辑直接解释了两个观察结果：

- 相同内容更新：原始记忆 ID 在双方都已失活，双方后继 ID 不同，即使后继内容完全一致仍会被判为冲突；
- 双方删除：原始记忆 ID 在双方都已失活，且双方均无后继记忆，仍会被判为冲突。

这一结论已对照固定版本 Memoria 源码中的 `memoria/crates/memoria-git/src/service.rs` 确认，并非仅根据两次 API 响应推测。
