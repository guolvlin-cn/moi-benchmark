# Memoria 快照与回滚能力正式实验报告

> 实验名称：快照与回滚正式实验 v1
> 实验日期：2026-08-12
> 正式结果：**50 个通过 / 0 个失败 / 0 个错误**
> 实验轨道：受控轨道（Controlled Track），直接写入结构化记忆

## 1. 实验摘要

本实验验证 Memoria 在创建快照后发生记忆新增、修改、删除及其组合变化时，能否将记忆空间恢复到指定快照状态，并使恢复后的状态重新通过检索接口可见。

正式数据集包含 50 个确定性用例，覆盖单一操作、混合操作、多快照跨级回滚、回滚后继续写入、重复回滚幂等性和边界/失败路径。每个用例使用独立用户空间，并通过一个完全独立的金丝雀用户检查跨用户污染。

在冻结的数据集、执行器和配置下：

- 50/50 个用例通过；
- 501/501 条必选断言通过；
- 62/62 次状态哈希比较一致；
- 116/116 条检索记录满足声明的可见性要求；
- 50/50 次金丝雀隔离检查通过；
- 无系统错误。

因此，本实验支持以下结论：

> Memoria 在本次冻结的 50 用例快照与回滚协议中，能够正确恢复被测试的记忆状态，并满足每个用例声明的检索恢复要求。

该结论仅针对本实验覆盖的确定性用例，不应扩大解释为“任意规模、任意并发、所有检索路径下均不会发生索引异常”。

## 2. 测试的能力是什么

快照与回滚不是单条记忆的修改历史，而是对一个用户记忆空间在某一时刻的整体状态进行保存和恢复。

本实验主要回答五个问题：

1. 能否为当前记忆空间创建快照；
2. 快照之后发生新增、修改或删除后，能否恢复到快照前状态；
3. 多个快照存在时，能否回滚到不同层级的历史状态；
4. 回滚后的记忆能否通过正常检索重新访问，快照之后产生的记忆是否从检索结果消失；
5. 不存在、已删除或重名快照等边界操作，是否按预期返回且不破坏当前状态。

实验将“回滚正确”拆为三个可独立审计的层次：

| 层次 | 核心检查 |
|---|---|
| API 行为 | 创建、回滚、删除快照的 HTTP 状态和返回内容是否符合预期 |
| 记忆状态 | 活动记忆 ID、内容、类型、元数据、状态等是否恢复为目标状态 |
| 检索可见性 | 应恢复的记忆能否检索到，快照后产生的记忆是否从结果中消失 |

正常用例只有状态和检索断言都通过才记为“通过”。预期失败用例必须返回指定错误，并保持原状态及检索行为不变。

## 3. 数据集构造

### 3.1 基本原则

正式数据集为 `snapshot-rollback-formal-v1.jsonl`，采用“初始状态 + 操作序列 + 查询 + 程序化断言”的确定性结构。

数据构造遵循以下规则：

- 每个用例对应一个独立 `user_id`；
- 记忆正文使用正常自然语言，不插入 `[SR_ADD_001]` 一类人工检索锚点；
- 用例 ID、记忆别名和字段名只保存在结构字段或元数据中；
- 写入使用 `POST /v1/memories`，不经过原生对话抽取；
- 运行时返回的真实记忆 ID 与数据集别名在执行时绑定；
- 回滚前必须先证明操作确实改变了状态；
- 正常用例同时包含状态检查和检索检查；
- 每次运行保留请求、响应、状态、历史、检索和断言明细。

### 3.5 典型操作流程

普通单快照用例的基本流程为：

```text
写入初始记忆
→ 捕获 baseline
→ 创建快照 S1
→ 执行新增/修改/删除
→ 捕获 mutated
→ 检索并确认变更可见
→ 回滚到 S1
→ 捕获 rolled_back
→ 检索并确认旧状态恢复
→ 执行状态、检索和隔离断言
```

多快照用例会额外创建 S2，并依次验证：

```text
latest → rollback S2 → state_s2 → rollback S1 → baseline
```

## 4. 实验协议与判定方法

### 4.1 用户隔离

50 个用例分别使用：

```text
feature-sr-formal-001
...
feature-sr-formal-050
```

另设金丝雀用户 `feature-sr-formal-canary`。执行器在每个用例完成后重新计算金丝雀状态哈希；任何变化都视为跨用户污染并导致该用例失败。

### 4.2 状态捕获与哈希

每次 `capture_state` 保存：

- 当前全部活动记忆；
- 已知记忆别名对应的历史；
- `active_state_hash`；
- `history_state_hash`；
- 捕获时间和用例用户。

活动状态哈希纳入以下字段：

- `memory_id`
- `user_id`
- `author_id`
- `subject_id`
- `memory_type`
- `content`
- `trust_tier`
- `initial_confidence`
- `is_active`
- `session_id`
- `observed_at`
- `extra_metadata`

为避免非语义运行噪声，`created_at` 和 `retrieval_score` 不进入严格状态哈希，但仍保留在原始产物中。

正式主判定使用 `active_state_hash`；历史同步记录用于审计，但本次没有将所有用例的 `history_state_hash` 一致性作为独立主指标。

### 4.3 检索判定

检索调用 `/v1/memories/retrieve`，每次 `top_k=20`。主要断言包括：

- `retrieval_contains`：指定别名必须出现；
- `retrieval_excludes`：指定别名不得出现；
- 必要时检查返回顺序或最大排名。

执行器允许最多 30 秒的检索可见性等待，轮询间隔 0.5 秒。本次正式运行的 116 条检索记录全部在第一次查询时满足要求，没有进入后续轮询。

### 4.4 用例状态定义

| 状态 | 定义 |
|---|---|
| 通过（PASS） | 所有必需断言和金丝雀隔离断言通过 |
| 失败（FAIL） | API 执行完成，但至少一条必需断言不通过 |
| 错误（ERROR） | 用例因请求、协议或执行器错误未完成 |

失败和错误用例均保留在总分母中，不静默排除。

## 10. 结果分析

### 10.1 已得到验证的能力

本实验对以下能力提供了直接证据：

- 单条记忆新增、修改、删除后的状态恢复；
- 多条记忆混合变化后的整体状态恢复；
- 多快照存在时回滚到不同历史层级；
- 删除记忆后以原 memory ID 恢复；
- 回滚后继续写入；
- 对同一快照重复回滚时保持幂等；
- 空快照和无变化回滚；
- 快照名规范化；
- 不存在及已删除快照的错误处理；
- 重复快照名不覆盖原快照；
- 用例间用户隔离；
- 声明查询下的回滚后检索恢复。

### 10.2 100% 结果应如何表达

推荐表述：

> Memoria 在冻结的 50 用例快照与回滚正式数据集中取得 50/50，通过全部 501 条状态、检索、错误路径和隔离断言。

不推荐表述：

> Memoria 的快照回滚在所有情况下绝对可靠，索引不会发生异常。

后者超出了实验覆盖范围。

### 10.3 为什么不使用阅读器或裁判模型

该实验评估的是平台状态机和检索可见性，不是自然语言问答质量。主要结果均能通过 API 状态、记忆 ID、内容、状态哈希和检索成员关系程序化判定，因此无需引入阅读器或裁判模型的生成随机性。

## 11. 实验边界与限制

1. **受控轨道**：记忆通过 `POST /v1/memories` 直接写入，不代表 `/v1/observe` 的原生记忆抽取效果。
2. **确定性功能集**：50 个用例不是随机压力测试，也不覆盖任意长操作链。
3. **无并发测试**：没有验证并发创建快照、并发写入或回滚原子性。
4. **检索覆盖有限**：每个用例验证声明的固定查询，不是对每条恢复记忆和每种检索路径进行穷举。
5. **未拆分检索通道**：没有分别评价向量检索、全文检索和混合检索的恢复行为。
6. **本地性能**：延迟来自本地 Mac 与 Docker，不能外推到生产环境。
7. **无竞品同条件对比**：本报告只验证 Memoria 自身能力，不把竞品的单条记忆历史等同于空间级快照与回滚。
8. **本地源码状态**：结果绑定提交号和源码差异哈希，需同时保留两者才能复现同一实现状态。
