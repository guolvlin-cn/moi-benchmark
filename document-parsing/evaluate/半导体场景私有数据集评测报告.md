# 半导体场景私有数据集文档解析评测报告

## 1. 评测概述

本次评测面向半导体业务场景中的复杂文档解析问题，对以下三套产品/服务进行比较：

- **MOI IDC 4.1.14**
- **MinerU Precision**
- **PaddleOCR-VL**

评测集共 50 份文件，覆盖 PDF、PPTX、DOCX、DOC 四种格式，其中单页文件 18 份、多页文件 32 份。样本重点包含跨页表格、复杂合并单元格、标题层级、页眉页脚、公式、流程图、图片与正文混排等实际问题。

评分包含公式、页眉页脚、图片、版式、表格检测、表格结构相似度（TEDS）、文本内容、标题层级八个有效维度。Caption 与 Reading Order 在本批 Golden 中没有有效计分样本，因此不纳入结论。

## 2. 实验配置与调用链路

本节记录的是本次评分所使用结果的实际生成方式。MOI 配置以最终结果 ZIP 内保存的 `parser_config` 为准；MinerU 与 PaddleOCR-VL 配置以批跑脚本中的实际请求参数为准。鉴权信息不写入报告。

| 实验 | 部署/服务 | 入口地址 | 核心模型或服务 |
|---|---|---|---|
| MOI | Matrixflow IDC 4.1.14，V2 Parser Pipeline | 本地 Catalog API：`http://127.0.0.1:8920/v1/genai/pipeline` | Paddle `PP-DocLayout_plus-L` + MinerU VLM + MOI V2 后处理 VLM |
| MinerU | MinerU Precision Extract API | `https://mineru.net/api/v4/file-urls/batch` | `model_version=vlm`；云服务未在结果中返回精确模型权重版本 |
| PaddleOCR-VL | 百度智能云“智能文档解析”在线服务 | `https://aip.baidubce.com/rest/2.0/brain/online/v2/paddle-vl-parser/task` | PaddleOCR-VL 在线模型；接口未提供模型版本选择参数，结果中也未返回精确版本号 |

### 2.1 MOI IDC 4.1.14

MOI 不是单一模型直出，而是以下组合链路：

1. 使用 Paddle `PP-DocLayout_plus-L` 检测版面与表格区域。本次设置 `use_remote_paddle_layout=false`，因此采用本地 CPU、FP32 推理，置信度阈值为 `0.4`。4.1.14 环境依赖为 `paddleocr 3.3.2`、`paddlepaddle 3.3.0` 和 `paddlex 3.3.13`。
2. 对 Paddle 检测到的表格区域进行涂白/占位，再交给 MinerU，避免同一表格被重复解析。
3. 调用 IDC MinerU：`https://shanghai.idc.matrixorigin.cn:30116/file_parse`，请求后端为 `vlm-vllm-async-engine`，开启公式、表格、Markdown、middle JSON、content list 和图片返回。对应部署镜像为 `mineru-vllm:v2.7.4`，其 VLM 模型为 `MinerU2.5-2509-1.2B`。
4. V2 Pipeline 合并 MinerU 文本块与 Paddle 表格块，再进行表格 HTML 重建、跨页表格合并、标题、页眉页脚、公式与列表修复等后处理。后处理主 VLM 为 `qwen3.5-27b`：其中 10 个结果在请求中显式指定该模型，其余 40 个结果未做请求级覆盖，继承 4.1.14 环境的同名主模型。

输入文件通过本地 Matrixflow Catalog API 提交；DOCX、PPTX 均设置 `convert_to_pdf=true`，PPTX 不转换成逐页图片。任务状态和结果 ZIP 分别通过 Workflow API 查询、下载：

- 状态查询：`http://127.0.0.1:8910/byoa/api/v1/workflow_job`
- 文件状态：`http://127.0.0.1:8910/byoa/api/v1/workflow_job/{job_id}/files`
- 结果下载：`http://127.0.0.1:8910/byoa/api/v1/explore/volumes/any/files/{file_id}/raws`

### 2.2 MinerU Precision

MinerU 使用 Precision Extract API 的批量上传流程：

- 申请上传地址：`POST https://mineru.net/api/v4/file-urls/batch`
- 上传文件：对接口返回的签名 URL 执行 `PUT`
- 查询结果：`GET https://mineru.net/api/v4/extract-results/batch/{batch_id}`
- 鉴权：`Authorization: Bearer <token>`

提交参数为：

```json
{
  "model_version": "vlm",
  "language": "ch",
  "enable_table": true,
  "enable_formula": true
}
```

服务完成后下载 `full_zip_url` 并解压，评分使用解压后的 Markdown、content list、layout 等结果。该 API 调用明确选择的是 MinerU 的 `vlm` 模式，不是 `pipeline`；但服务响应及保留结果未提供精确模型名称、参数量或发布版本，因此本报告不将其进一步写成某个无法核实的 MinerU 权重版本。

### 2.3 百度智能云 PaddleOCR-VL

PaddleOCR-VL 使用百度智能云异步智能文档解析接口：

- 获取 Access Token：`POST https://aip.baidubce.com/oauth/2.0/token`
- 提交任务：`POST https://aip.baidubce.com/rest/2.0/brain/online/v2/paddle-vl-parser/task`
- 查询任务：`POST https://aip.baidubce.com/rest/2.0/brain/online/v2/paddle-vl-parser/task/query`

原文件以 Base64 写入 `file_data`，同时传入文件名。本次启用的解析参数为：

```text
analysis_chart=true
merge_tables=true
relevel_titles=true
recognize_seal=true
return_span_boxes=true
```

任务成功后分别下载 `markdown_url` 与 `parse_result_url`，评分使用返回的 Markdown 和 JSON。该端点对应百度智能云的 PaddleOCR-VL 在线文档解析能力，但请求中没有模型版本字段，返回 JSON 也没有模型版本信息，因此这里记录为“PaddleOCR-VL 在线服务”，不推断其内部具体 checkpoint。

## 3. 核心结论

**MOI 在该私有数据集上取得显著领先，并且优势具有较强的一致性。**

- MOI 文件内维度等权、文件间等权平均分为 **84.5%**，高于 PaddleOCR-VL 的 **58.6%** 和 MinerU 的 **56.8%**。
- MOI 文件内按元素数量加权、文件间等权平均分为 **89.4%**，高于 PaddleOCR-VL 的 **70.5%** 和 MinerU 的 **66.7%**。
- 50 个文件中，MOI 在 **42 个文件**上取得最高等权分；PaddleOCR-VL 领先 6 个，MinerU 领先 2 个。
- MOI 没有解析失败；PaddleOCR-VL 有 1 个 PPTX 返回接口成功但结果为空，应按有效解析失败处理。

| 产品 | 文件内维度等权分（50 文件等权） | 文件内元素数量加权分（50 文件等权） | 单文件领先数 | 有效解析失败 |
|---|---:|---:|---:|---:|
| **MOI IDC 4.1.14** | **84.5%** | **89.4%** | **42/50** | **0** |
| PaddleOCR-VL | 58.6% | 70.5% | 6/50 | 1 |
| MinerU Precision | 56.8% | 66.7% | 2/50 | 0 |

两种总分都先计算每个文件的得分，再对 50 个文件等权平均。它们的区别只在单文件内部：前者对该文件的有效评测维度等权，后者根据各维度的元素数量加权。因此，后者不是将 50 个文件的全部元素合并后计算的全局 Micro Average，一个大文件和一个小文件在最终总分中的权重始终都是 **1/50**。

两种口径的结论一致，说明 MOI 的优势在文件内的维度覆盖和元素数量结构下都能保持，同时不会让元素数量特别多的少数文件主导最终总分。

## 4. 多维度能力分析

| 维度 | MOI | PaddleOCR-VL | MinerU | MOI 相对最优竞品领先 |
|---|---:|---:|---:|---:|
| 版式 Layout | **96.4%** | 88.5% | 84.7% | +7.9 pp |
| 公式 | **91.9%** | 33.4% | 9.8% | +58.5 pp |
| 标题层级 | **87.1%** | 64.1% | 43.7% | +23.0 pp |
| 表格检测 | **84.6%** | 68.6% | 75.0% | +9.6 pp |
| 页眉页脚 | **84.7%** | 33.1% | 39.2% | +45.6 pp |
| 图片 | **79.7%** | 43.7% | 43.5% | +36.0 pp |
| 文本内容 | **82.7%** | 66.2% | 62.3% | +16.5 pp |
| 表格结构 TEDS | **73.1%** | 38.9% | 51.0% | +22.1 pp |

### 4.1 MOI 的主要优势

1. **版式解析稳定**

   MOI 的 Layout F1 达到 96.4%，是所有能力中最稳定的一项。竞品在基础版式上也有一定能力，因此该维度领先幅度相对较小，但 MOI 的绝对分最高。

2. **公式、页眉页脚和图片处理优势突出**

   公式维度领先最明显，MOI 达到 91.9%，说明其对块级公式、图片公式及公式数量的处理明显优于竞品。页眉页脚和图片维度分别领先约 46 和 36 个百分点，是整体差距的重要来源。

3. **标题语义与层级恢复更可靠**

   MOI 标题层级 F1 为 87.1%，在“标题被识别成页眉”“正文误判为标题”“标题位于文档中间”等场景中整体表现更稳定。

4. **表格不仅检出率高，结构还原也更好**

   MOI 的表格检测 F1 为 84.6%，结构 TEDS 为 73.1%，均为最高。说明优势不仅是“找到了表格”，还体现在合并单元格、跨页拼接和复杂表格 HTML 结构的恢复质量上。

### 4.2 仍需重点改进的方向

- **表格结构 TEDS 是 MOI 当前绝对分最低的维度（73.1%）**。虽然显著领先竞品，但距离稳定还原复杂表格仍有空间。
- **PDF 是 MOI 相对较弱的格式**。PDF 文件等权平均分为 74.9%，低于 Office 文件的 88.5%。
- 部分基础 PDF、标题语义和 PPT 截图类 case 上，PaddleOCR-VL 或 MinerU 表现更好，例如：
  - `基础解析_01.pdf`
  - `97TagDes带正文识别为标题.docx`
  - `197PPT中的截图被拆分.pptx`
  - `58企业复杂绩效指标与深度战略分析.pdf`

这些样本适合作为 MOI 下一轮定向回归集。

## 5. MOI 是否在多页文件上有优势

结论是：**有明显优势，尤其在长文档和多页表格场景中；但 MOI 的领先并不只来自多页能力。**

| 文件分组 | 文件数 | MOI 等权分 | PaddleOCR-VL | MinerU |
|---|---:|---:|---:|---:|
| 单页 | 18 | **82.3%** | 55.9% | 54.5% |
| 多页（2页及以上） | 32 | **85.7%** | 60.0% | 58.1% |
| 2～4页 | 14 | **84.1%** | 65.9% | 59.1% |
| 5页及以上 | 18 | **86.9%** | 55.5% | 57.3% |
| 多页且包含表格 | 27 | **86.7%** | 59.0% | 59.8% |
| 显式跨页/多页问题样本 | 8 | **81.8%** | 52.3% | 56.6% |

从结果看：

- MOI 在多页文件上的等权分为 85.7%，并且 5 页以上组高于 2～4 页组。
- 在 5 页及以上文件中，MOI 达到 86.9%，相对最优竞品领先约 29.6 个百分点。
- 在多页且包含表格的 27 个文件中，MOI 达到 86.7%，相对最优竞品领先约 26.9 个百分点。
- 8 个名称明确指向跨页表格或多页问题的样本中，MOI 全部取得最高分。

典型样本包括：

- `0625跨页表合并复现case.docx`：MOI 97.0%，竞品最高 70.4%。
- `跨页表合并QR.pdf`：MOI 87.0%，竞品最高 57.7%。
- `114跨页表识别为两张表_old.docx`：MOI 91.4%，竞品最高 69.5%。
- `12测试跨页表的拼接.pdf`：MOI 53.2%，竞品最高 32.4%。该样本三方得分都不高，说明仍是共同难点。

不过，MOI 在单页文件上同样领先约 26 个百分点，因此不能把总体优势完全归因于多页处理。更准确的结论是：

> MOI 的基础解析能力已经领先，并且这种优势在长文档、跨页表格和多页 Office 文档中能够保持或进一步扩大。

## 6. 不同文件格式表现

| 格式 | 文件数 | MOI 等权分 | PaddleOCR-VL | MinerU |
|---|---:|---:|---:|---:|
| DOCX | 18 | **92.5%** | 56.6% | 63.9% |
| DOC | 4 | **85.3%** | 46.4% | 60.9% |
| PPTX | 13 | **84.1%** | 63.7% | 44.2% |
| PDF | 15 | **74.9%** | 59.6% | 58.2% |

MOI 在四种格式上均取得最高平均分，其中：

- **DOC/DOCX 是最强项**，说明 Office 文档结构、标题、页眉页脚和跨页表格处理形成了明显优势。
- **PPTX 整体领先明显**，并避免了 PaddleOCR-VL 在非空 PPTX 上返回空结果的问题。
- **PDF 仍然领先，但优势收窄**，是后续最值得投入的格式方向。

## 7. 产品定位与建议

### 7.1 可对外表达的结论

基于当前私有数据集，可以较有把握地表述：

> MOI 在半导体场景复杂文档解析中整体领先，优势集中在 Office 文档、多页文件、跨页表格、公式、页眉页脚、图片及标题层级恢复；其中对 5 页以上长文档和多页表格的处理稳定性尤其突出。

不建议只表述为“MOI 擅长多页文件”，因为数据同时表明 MOI 在单页和基础版式上也有明显优势。

### 7.2 后续优化优先级

1. 以表格 TEDS 为第一优化目标，重点处理复杂合并单元格、无线表格和跨页拼接后的结构一致性。
2. 针对 PDF 单独建立回归子集，分析基础 PDF、复杂图文 PDF 和流程图 PDF 的失分来源。
3. 将竞品领先的 8 个文件作为困难负样本，避免总体高分掩盖局部能力缺口。
4. 保留 PaddleOCR-VL“接口成功但输出为空”的失败判定规则，防止形式成功抬高有效成功率。

## 8. 评分工具与复现方法

本次统一评分使用 `moi-parsing-benchmark 1.0.0`。正式评分日期为 2026-07-31，复现时固定使用在该日期前最新的 `matrixorigin/moi-parse-bench` commit：

```text
06faf76112c998835f0f9ca174a5f2d311d559f2
```

评分输入和聚合步骤如下：

1. MOI：从每个结果 ZIP 中提取唯一的 `*_parse.json`。
2. MinerU：使用上述 commit 中的 `tools/parsing_benchmark/tools/mineru_content_list_to_parsed`，将非 V2 的 `*_content_list.json` 转换为统一 Parse Blocks。
3. PaddleOCR-VL：使用 `scripts/adapt_paddleocr_vl_to_parsed.py` 将每个 `result.json` 转换为统一 Parse Blocks。
4. 使用 `parsing_benchmark.runner.BenchmarkRunner(strict_contract=false)` 对每个 parsed JSON 与对应 Golden 单独评分。每个维度的 P/R/F1 在进入总分前按评分器契约保留 4 位小数。
5. 单文件维度等权分是该文件所有有效维度 F1 的算术平均；单文件元素加权分使用该维度 `total_count` 为权重。最后对 50 个文件等权平均。
6. PaddleOCR-VL 若接口返回成功但转换后 `blocks=[]`，该文件仍保留在 50 文件分母中，所有适用维度计 0。

一键复算：

```bash
cd moi-benchmark
bash document-parsing/scripts/reproduce_semiconductor_private_score.sh
```

脚本会从本地 `moi-parse-bench` Git 对象中导出固定 scorer commit，不使用该仓库当前工作区代码；输出写入 `evaluate/semiconductor-private-final/reproduced-score.json`，并自动校验三套系统的两个总分。

如需从竞品原始返回重新生成 `converted_parsed`，使用 `scripts/adapt_semiconductor_private_outputs.py`。详细命令、目录关系和产物说明见 `evaluate/semiconductor-private-final/README.md`。

当前仓库中的 `run_local_v2_semiconductor_4_1_14.py` 是后来形成的统一重跑配置，不等同于本次正式结果的 4 个历史小批次。正式配置以 ZIP 内 `parser_config` 和 `semiconductor-private-final/manifest.json` 为准。

## 9. 结果解释边界

- 本次结论仅针对这 50 份半导体场景问题样本，不等价于通用文档市场的全面排名。
- 总分的两种口径都是文件间等权平均，分母始终为 50；“元素数量加权”仅发生在单文件内部。
- 数据集以历史问题和困难 case 为主，适合比较复杂场景能力，但格式与问题类型并非随机采样。
- 三个产品的版本、部署环境和配置不同；本报告比较的是本次实际可交付结果，而不是纯模型能力。
- MOI 的 50 个结果包含上述 4 个配置小批次；MinerU Precision 与 PaddleOCR-VL 的云端接口均未返回精确模型权重版本。跨产品差异中同时包含模型、工程链路和后处理的影响。
- Caption 与 Reading Order 没有有效计分样本，不能据此判断三方在这两个维度上的能力。
- 多页分析统一使用评测表中的 Golden/源文件页数，避免采用不同解析器输出页数造成分组偏差。
- 当前 Golden 与 `/Users/wangyaqi/Documents/cursor_project/moi-parse-bench/datasets/parse` 中的 50 份 Golden 逐文件 SHA-256 一致，50 份均已标记为 reviewed。2026-08-14 更新的 8 份 Golden 仅清除了待复核字段并确认复核状态，计分字段未变化，因此三套系统的正式分数不受影响。
