## 失败原因

51 次严格判错记录按直接比较原因统计：

| 原因 | 次数 | 说明 |
|---|---:|---|
| 返回列数不一致 | 21 | 最常见；SQL 往往包含正确答案，但多返回辅助统计列或少返回要求列 |
| 有序结果值不一致 | 21 | 其中 8 次只是 MySQL 与 MatrixOne 默认字符串排序规则不同 |
| 行数不一致 | 3 | 主要是查询范围、JOIN 或 LIMIT 与 Golden 不同 |
| 无序结果值不一致 | 2 | 查询值或过滤逻辑与 Golden 不同 |
| SQL 执行失败 | 1 | `e12` 第一轮错误使用 `enron_emailorig.date` |
| 超时 | 3 | `e03` 第三轮、`m17` 第二轮、`h02` 第二轮超过 300 秒；超时包含在上述 51 次失败中 |

典型遗留问题：

- `e11`：三轮均只返回日期、主题和发件人 3 列，而 Golden 口径还要求邮件 ID，共 4 列。
- `e16`：问题只要求最大邮件数量，MOI 三轮都额外返回 mailbox。
- `m05`：平均收件人数逻辑基本成立，但额外返回 email_count，严格列结构不匹配。
- `m06`：要求百分比单列，MOI 额外返回分子和分母。
- `m10`：仍使用当前收件人 `enron_emailto`，没有按规则使用 `enron_emailorig` 的原始发件人。
- `h05`：三轮返回结构不同，仍未稳定满足“最忙日期及当天前 5 个发件人”的三列口径。
- `h08`：仍受自然语言歧义影响，三轮分别理解为按两人分组的收件情况或单人汇总，没有稳定计算 Golden 定义的共同收件人。

## 跨引擎排序辅助口径

`e10` 三轮、`h02` 第一和第三轮、`h07` 三轮的行集合与 Golden 完全相同，只是 MySQL 与 MatrixOne 默认字符串排序规则不同。这 8 次在严格主口径中仍判失败；若单独采用“忽略数据库默认 Collation 差异”的辅助口径，则可记为 107/150（71.33%）。该辅助值不能替代正式的 99/150（66.00%）。

## 判定说明

- Golden SQL 在 MySQL 8 执行；MOI 使用对话过程中实际保存的 MatrixOne 原生执行结果，不把 MOI SQL 重新放到 MySQL 执行。
- Golden 含 `ORDER BY` 时进行有序比较，否则进行无序比较。
- 列数、行数和规范化后的值必须一致；额外返回未要求的列也判为不一致。
- MOI 一题执行多条 SQL 时，只比较最终答案引用的结果集；任一被引用结果与 Golden 完全一致即可通过。
- 分页结果按相同列结构合并后再比较。
- Repeat Correct Rate 要求同一题三轮的执行结果都与 Golden 一致，不要求三轮 SQL 文本相同。
- 本报告是自动严格评分；此前约定的人工审核修正应作为附加结果保留，不能覆盖这份原始自动成绩。
