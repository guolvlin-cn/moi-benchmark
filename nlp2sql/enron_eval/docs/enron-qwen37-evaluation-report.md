# Enron 私有数据集 NL2SQL 产品评测报告

> 评测模型：`qwen3.7-plus-2026-05-26`  
> 数据冻结版本：`enron_qwen37_reference_20260813`  
> 数据来源提交：`71c1d9cbd8fe91d2f5afbd4c106d373bbac39a2e`  
> 报告日期：2026-08-13

## 1. 评测结论摘要

本次评测使用同一大模型，对 Chat2DB、Wren AI 和 MOI 三个 NL2SQL 产品进行了对比。MOI 同时测试了“无语义配置”和“有语义配置”两种状态，因此共有四组有效结果。

主要结论如下：

- Chat2DB 的人工复核严格正确率最高，为 **87.33%**；稳定正确率最高，为 **82%**；同时端到端延时最低。
- MOI 加入语义配置后的人工复核严格正确率为 **86.67%**，与 Chat2DB 接近；在口语化问题上达到 **82.67%**，是四组配置中最高的。
- MOI 语义配置相对无语义配置，整体严格正确率提升 **10 个百分点**，口语化问题严格正确率提升 **20 个百分点**，说明业务语义配置对自然语言理解有明显帮助。
- Wren 本轮存在较多未生成 SQL、超时和执行失败，人工复核严格正确率为 **44.00%**，端到端延时也明显高于另外两个产品。
- 自动结果完全匹配会把大小写排序、列数差异、合理的替代语义等情况判错，因此本报告同时保留自动评测原始分数和人工复核分数。
- 口语化会降低所有配置的准确率，但 MOI 加语义配置后的下降最小，说明语义层能够缓解用户表达不精确带来的影响。

本报告不把准确率、延时和 Token 强行合成为一个总分。不同指标分别展示，避免人为权重掩盖产品特点。

## 2. 评测目标

本次评测重点观察以下五个方面：

1. 产品能否生成非空、安全且可以执行的 SQL。
2. SQL 执行结果是否满足问题要求。
3. 同一问题连续运行三次时，是否能够稳定得到正确结果。
4. 用户口语化表达是否会降低准确率，以及语义配置能否缓解这一问题。
5. 产品从收到问题到返回 SQL 和结果需要多长时间，并记录可获得的 Token 消耗。

## 3. 参评产品与统一条件

| 产品配置 | 部署及数据环境 | 业务语义配置 | 大模型 |
|---|---|---:|---|
| Chat2DB | 购买会员的商业桌面软件；连接本地 MySQL `enron_eval` | 无 | `qwen3.7-plus-2026-05-26` |
| Wren AI | 本地 Docker 部署的 Canner/WrenAI；通过数据桥连接同一 MySQL | 无专门业务语义 | `qwen3.7-plus-2026-05-26` |
| MOI 无语义 | 本地 Matrixflow/MOI；Enron 数据导入 MatrixOne 知识库 | 无 | `qwen3.7-plus-2026-05-26` |
| MOI 有语义 | 与上一组使用相同 MOI 数据和知识库流程 | 有，导入完整 Enron 语义配置 | `qwen3.7-plus-2026-05-26` |

统一模型的目的是尽量减少基础模型能力差异，让结果更集中地反映产品自身的 Schema 探索、语义理解、SQL 生成、反思修正和执行能力。

需要注意：Chat2DB 和 Wren 的候选 SQL 在 MySQL 中执行；MOI 的 SQL 在 MatrixOne 知识库中生成并执行，再将执行结果与 Golden SQL 在 MySQL 中得到的结果进行规范化比较。这是 MOI 产品真实使用路径，但也引入了数据库引擎、大小写和排序规则差异。

## 4. 数据集与题目覆盖面

### 4.1 数据库范围

评测数据库版本为 `enron_eval_v1`，包含 **6 张表、32 个字段、10,401 封邮件**。

| 表名 | 行数 | 主要含义 |
|---|---:|---|
| `enron_email` | 10,401 | 邮件主体及邮件目录信息 |
| `enron_emailinfo` | 10,401 | 当前邮件的日期、主题、发件人等标准头信息 |
| `enron_emailorig` | 1,161 | 正文中解析出的历史引用邮件头，用于回复链分析 |
| `enron_emailto` | 71,670 | 标准收件邮箱展开表 |
| `enron_emailxto` | 72,349 | 原始展示收件人展开表 |
| `enron_source` | 10,401 | 邮件来源员工、PST 文件和原始目录信息 |

### 4.2 题目构成

评测集固定为 50 题，每题重复运行 3 次，共 **150 次请求**。

| 维度 | 数量 |
|---|---:|
| Easy | 20 |
| Medium | 20 |
| Hard | 10 |
| 明确语义题 | 25 |
| 用户口语化题 | 25 |

题目覆盖：

- 单表过滤、去重和计数；
- 分组、聚合、排序、Top N 和百分比；
- 多表 JOIN、反连接、交集和集合关系；
- 发件地址、显示发件人、标准收件地址和原始展示收件人的区分；
- 当前邮件头与历史引用邮件头的区分；
- 员工邮件目录、PST 来源文件和邮箱文件夹；
- 日期字符串解析、邮件线程主题标准化和回复关系；
- 精确查询条件与带有真实用户表达习惯的模糊语义。

“明确语义题”和“口语化题”各占一半，可以同时观察 SQL 能力和自然语言理解能力，而不只评价模型能否照着技术描述翻译 SQL。

## 5. 评测流程

每个产品均采用相同的基本流程：

1. 固定数据库版本、50 道问题、Golden SQL 和统一模型。
2. 每道题建立独立会话或独立请求上下文。
3. 每道题运行 3 次，记录产品生成的 SQL、执行状态、执行结果、端到端时间和可获得的 Token。
4. 自动在目标数据库中执行候选 SQL，并与 Golden SQL 的执行结果进行规范化比较。
5. 保留自动评测原始结果，不因人工审核而修改。
6. 对自动判错、未展示结果或可能存在合理替代解释的记录进行人工复核。
7. 分别统计总体、明确语义题、口语化题，以及三次重复运行的稳定性。

## 6. 指标定义

### 6.1 四项核心指标

| 指标 | 计算方式 | 说明 |
|---|---|---|
| Execution Accuracy | 与 Golden 执行结果一致的请求数 ÷ 150 | 判断最终查询结果是否正确 |
| SQL Success Rate | 生成非空、安全且成功执行 SQL 的请求数 ÷ 150 | 判断产品能否稳定交付可运行 SQL |
| End-to-end Latency | 150 次请求耗时的 P50、P95和平均值 | 从提交问题到产品返回 SQL/结果的完整等待时间 |
| Repeat Correct Rate | 三次运行均正确的题目数 ÷ 50 | 判断同一问题重复提问时是否稳定正确 |

其中：

- P50 表示一半请求的耗时不超过该值，反映普通请求体验。
- P95 表示 95% 请求的耗时不超过该值，反映慢请求和长尾体验。
- 端到端延时包含产品 Agent 分析、模型调用、工具调用和 SQL 执行，并不是单独的大模型推理时间。

### 6.2 人工复核口径

自动评测数据保持不变，人工复核另外产生三种统计：

| 标签 | 分值 | 判断标准 |
|---|---:|---|
| 正确 | 1 | SQL 和结果满足问题核心要求 |
| 部分正确 | 0.5 | 核心语义基本正确，但存在非关键列、排序、展示或边界问题 |
| 错误 | 0 | 核心语义、数据范围、表字段、计算逻辑或结果错误 |

- 人工严格正确率：仅“正确”计 1 分。
- 人工加权正确率：“正确”计 1 分，“部分正确”计 0.5 分。
- 人工稳定正确率：同一题三次均被判定为“正确”的题数 ÷ 50。

### 6.3 Token 消耗

Token 指标记录产品评测流程中可观测到的大模型 Token。由于不同产品的内部提示词、Agent 调用次数、缓存机制和日志暴露程度不同，Token 只能用于观察调用成本量级，不能视为完全同口径的产品成本排名。

## 7. 自动评测原始结果

以下结果由脚本直接比较候选 SQL 与 Golden SQL 的执行结果，未经过人工修正。

| 产品配置 | SQL Success Rate | Execution Accuracy | Repeat Correct Rate | 延时 P50 | 延时 P95 | 平均延时 |
|---|---:|---:|---:|---:|---:|---:|
| MOI 有语义 | 146/150（97.33%） | 99/150（66.00%） | 29/50（58%） | 21.22 s | 173.25 s | 56.76 s |
| MOI 无语义 | 150/150（100%） | 85/150（56.67%） | 26/50（52%） | 25.76 s | 116.90 s | 46.17 s |
| Chat2DB | 150/150（100%） | 77/150（51.33%） | 21/50（42%） | 20.01 s | 69.91 s | 32.69 s |
| Wren AI | 114/150（76.00%） | 49/150（32.67%） | 12/50（24%） | 90.68 s | 180.89 s | 102.29 s |

补充说明：

- Chat2DB 和 MOI 无语义均在 150 次请求中生成并成功执行了 SQL。
- MOI 有语义有 3 次超时未取得 SQL，另有 1 次 SQL 执行失败。
- Wren 在 150 次请求中生成 119 条 SQL，其中 114 条成功执行；其余请求主要为超时、未生成 SQL或执行错误。
- Chat2DB 记录到的平均 SQL 数据库执行时间约为 40.25 ms，远小于 32.69 s 的端到端平均耗时，说明主要时间花在产品 Agent 和大模型流程，而不是数据库执行。

自动分数低于人工分数的主要原因，是自动比较会把以下记录直接判错：

- 结果集合相同但大小写排序或数据库排序规则不同；
- 额外返回一个不影响答案的辅助列；
- SQL 语义合理，但采用了与唯一 Golden 不同的解释；
- 页面分页或结果采集不完整；
- 日期、空值或字符串规范化方式不同。

## 8. 人工复核后的总体结果

| 产品配置 | 严格正确率 | 加权正确率 | 稳定正确率 | SQL Success Rate |
|---|---:|---:|---:|---:|
| Chat2DB | **131/150（87.33%）** | 131.5/150（87.67%） | **41/50（82%）** | **150/150（100%）** |
| MOI 有语义 | 130/150（86.67%） | **132/150（88.00%）** | 38/50（76%） | 146/150（97.33%） |
| MOI 无语义 | 115/150（76.67%） | 124/150（82.67%） | 35/50（70%） | **150/150（100%）** |
| Wren AI | 66/150（44.00%） | 69.5/150（46.33%） | 15/50（30%） | 114/150（76.00%） |

结果解读：

- Chat2DB 严格正确率和三轮稳定性最高，说明它在本数据集上的结果交付较稳定。
- MOI 有语义的加权正确率最高，并且与 Chat2DB 的严格正确率只相差 0.66 个百分点。
- MOI 无语义已经具备较高 SQL 成功率，但对业务表含义和口语表达的理解明显弱于有语义版本。
- Wren 的正确率不仅受到 SQL 逻辑错误影响，也受到未生成、超时和执行失败影响。

## 10. MOI 语义配置效果

| 指标 | MOI 无语义 | MOI 有语义 | 变化 |
|---|---:|---:|---:|
| 自动 Execution Accuracy | 56.67% | 66.00% | +9.33 个百分点 |
| 自动 Repeat Correct Rate | 52% | 58% | +6 个百分点 |
| 人工严格正确率 | 76.67% | 86.67% | **+10 个百分点** |
| 人工加权正确率 | 82.67% | 88.00% | +5.33 个百分点 |
| 人工稳定正确率 | 70% | 76% | +6 个百分点 |
| 口语题严格正确率 | 62.67% | 82.67% | **+20 个百分点** |
| 口语题稳定正确率 | 52% | 72% | **+20 个百分点** |

语义配置主要补充了以下内容：

- `from` 与 `xfrom`、`to` 与 `xto` 的业务区别；
- `enron_emailinfo` 当前邮件头与 `enron_emailorig` 历史引用邮件头的区别；
- `enron_source` 表中的员工来源、PST 文件和目录含义；
- 回复邮件、原始发件人和 `nth=1` 等回复链规则；
- 邮箱地址统一使用 `LOWER(TRIM(...))` 规范化；
- 邮件线程主题的 `Re:` 标准化；
- 日期字段是邮件头字符串，不能直接按普通字符串判断时间先后；
- 统计收件人数时是否按邮件 ID 去重，以及 `LEFT JOIN` 对零收件邮件的影响。

改进最明显的是口语题：用户只说业务概念、没有给出表字段时，有语义 MOI 更容易选择正确的数据来源。仍然出错的部分主要集中在回复链的复杂语义、日期解析、排序规则、返回列边界和个别超时。

## 11. 延时与 Token

| 产品配置 | 延时 P50 | 延时 P95 | 平均延时 | Token 总量 | 平均 Token/可观测请求 |
|---|---:|---:|---:|---:|---:|
| Chat2DB | **20.01 s** | **69.91 s** | **32.69 s** | 4,178,028 | 27,853.52 |
| MOI 无语义 | 25.76 s | 116.90 s | 46.17 s | 9,491,890 | 63,279 |
| MOI 有语义 | 21.22 s | 173.25 s | 56.76 s | 8,613,748 | 58,597（147/150 可观测） |
| Wren AI | 90.68 s | 180.89 s | 102.29 s | 不可获得 | 不可获得 |

分析：

- Chat2DB 的 P50、P95 和平均延时均最低，本轮交互速度最好。
- MOI 的典型请求速度接近 Chat2DB，但 P95 较高，说明存在明显长尾；有语义版本的个别请求接近或超过 3 分钟。
- Wren 的中位延时已经达到 90.68 秒，且较多请求触及约 180 秒超时边界，慢的主要原因是后台生成链路、服务稳定性和模型调用等待，不只是本地 MySQL 执行。
- MOI 的 Token 量明显高于 Chat2DB，说明其 Agent 探索、反思和工具调用链路更长；这可能提高复杂语义处理能力，也带来成本和长尾延时。
- Wren 当前接口没有返回可靠 Token usage，因此不能补算 Token。报告不使用估算值替代真实日志。

## 12. 典型错误与原因

| 类型 | 代表问题 | 现象 | 主要原因 |
|---|---|---|---|
| 业务语义歧义 | `m02_phillip_recipients` | Phillip Allen 被映射为一个或多个邮箱 | 问题中的“某人”没有天然限定唯一邮箱身份 |
| 回复链理解错误 | `m10_phillip_reply_orig_senders` | 查询当前收件人，而不是历史邮件头中的原始发件人 | `emailto` 与 `emailorig` 的业务角色混淆 |
| 计数去重错误 | `m07` | 得到 1243 而不是 1241 | 使用 `COUNT(*)`，未按邮件 `id` 去重 |
| JOIN 范围错误 | `m05_avg_recipients_per_email` | 比 Golden 多 1 行或平均值不同 | `INNER JOIN`/`LEFT JOIN` 选择及零收件邮件处理不同 |
| 日期排序错误 | `e11` | 星期字符串靠前，但不代表邮件时间最近 | 邮件日期是头信息字符串，直接 `ORDER BY date` 是字符排序 |
| 大小写及排序规则 | `e10`、`h02`、`h07`、`m20` | 集合相同但行顺序不同 | MySQL 与 MatrixOne 的字符排序及大小写规则不同 |
| 返回列边界 | `h05` 等 | 核心答案正确，但多列或少列 | 产品对“给我日期、主题和发件人”等输出要求遵循不完整 |
| 页面采集问题 | Chat2DB `e10` | 页面有完整回答，自动记录显示不完整 | 结果分页或采集器只截取部分页面状态 |
| 未生成或超时 | 多个 Wren 请求、少量 MOI 请求 | 没有 SQL 或到达 180/300 秒超时 | 后台链路稳定性、服务负载或模型调用等待 |

这些问题应分开处理：业务语义问题适合通过语义配置、字段说明和关系示例改进；排序、日期、去重和 JOIN 问题需要加强 SQL 生成规则或执行后校验；超时和未生成则属于产品可靠性和可运维性问题。

## 13. 评测限制与公平性说明

1. 本评测是自建的 Enron 私有数据集，共 50 题，不能代替 Spider 等公开基准，也不能代表所有数据库场景。
2. 25 道口语化题中存在真实用户语言常见的歧义。唯一 Golden SQL 只能代表预设口径，不能覆盖所有合理理解，因此必须保留人工复核。
3. 人工复核存在一定主观性。本项目保存逐题、逐轮的标签和备注，保证结论可以追溯。
4. MOI 使用 MatrixOne 原生执行路径，Chat2DB 和 Wren 使用 MySQL。跨引擎比较可能受到日期函数、大小写、排序规则和空值行为影响。
5. 只有 MOI 同时测试了有语义和无语义配置。Chat2DB 与 Wren 本轮没有建立等价的业务语义层，因此 MOI 的语义配置结果应视为产品增强方案，而不是完全同条件的裸模型比较。
6. 三个产品虽然统一使用同一大模型，但内部系统提示词、Schema 检索、Agent 工具链、反思策略和上下文长度不同。这正是本次产品级评测希望观察的差异。
7. Token 统计口径不完全统一，Wren 又缺少 Token 数据，因此 Token 只做辅助观察，不参与准确率排名。

## 14. 综合判断

在本次 Enron 邮件问答评测中：

- 如果优先看严格正确率、三轮稳定性和交互速度，Chat2DB 表现最好。
- 如果优先看口语化业务问题的理解，以及语义层带来的提升，MOI 有语义版本表现最好。
- MOI 无语义版本证明平台基础 SQL 交付能力稳定，但业务语义配置是提升真实用户问题准确率的关键。
- Wren 当前结果首先受到生成成功率和超时影响；在继续比较 SQL 逻辑能力前，需要先提高本地服务和推理链路的稳定性。

因此，本次评测不建议只公布一个“总分”，而应至少同时公布：SQL Success Rate、人工复核正确率、Repeat Correct Rate、P50/P95 延时、Token，以及明确语义和口语化两条赛道的结果。

## 15. 后续工作

下一版本建议按以下顺序推进：

1. 冻结当前四组原始记录、自动评分和人工标注，作为可复现基线。
2. 更换数据集或者增加题目数量多次评测，完善口语题的答案（这里感觉还是考虑使用公开数据集）：对确有歧义的问题允许多个等价 Golden 或明确人工判定规则。
3. 在核心四指标稳定后，再增加 SELECT、WHERE、JOIN、GROUP BY、ORDER BY 和函数等 SQL 结构级评测。
4. 后续如时间允许，在同一模型、同一数据和同一评分脚本下增加阿里云 DataAgent。
