> 文档状态：持续补充
>

## 项目概述

本项目使用固定的 Enron 邮件数据库快照、50 道中文问题和对应 Golden SQL，对 MOI、Wren AI、Chat2DB 三个产品的 NL2SQL 能力进行统一评测。

评测重点是最终产品能否理解中文问题、正确选择六张邮件相关表及字段、生成安全可执行的 SQL，并返回与 Golden SQL 等价的查询结果。三个产品使用相同数据、问题、数据库权限、模型和评分脚本，减少外部变量对结果的影响。

历史评测已经保留各产品原有模型下的结果。后续统一模型评测必须建立新批次，不覆盖历史结果。

## 模块一：统一模型选型

### 1. 选型结论

三个产品统一使用阿里云百炼提供的 OpenAI 兼容接口：

| 配置项 | 固定值 |
|---|---|
| 模型服务平台 | 阿里云百炼 Model Studio |
| API协议 | OpenAI兼容 Chat Completions |
| Base URL | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| 生成模型 | `qwen3.7-plus-2026-05-26` |
| Temperature | `0` |
| Max Tokens | `4096` |
| 数据地域 | 华北2（北京） |

正式评测优先使用固定快照 `qwen3.7-plus-2026-05-26`，而不是会随平台升级的动态别名 `qwen3.7-plus`。这样可以保证不同产品和不同日期的运行使用同一模型版本。

如果任一产品不能传入固定快照模型ID，则暂停正式运行；只有三个产品都验证支持后才能开始50题评测。不得让一个产品使用快照、另一个产品使用动态别名。

### 2. 为什么固定使用阿里云百炼

第一，公司已经具备可用的阿里云百炼 API Key，不需要为三个产品分别采购或维护不同模型服务账号。

第二，MOI、Wren AI 和 Chat2DB 都支持 OpenAI 兼容接口，可以使用同一个 Base URL、模型ID和密钥来源，降低接入差异。

第三，统一模型服务后，产品得分差异主要来自 Schema 检索、语义层、提示词、SQL生成流程、自动修复和产品交互，而不是来自底层模型不同。

第四，阿里云百炼提供调用记录和用量数据，后续可以补充时延、Token和成本分析。API Key只保存在各产品本机私有配置中，不写入本仓库。

### 3. 为什么选择Qwen3.7 Plus固定快照

`qwen3.7-plus-2026-05-26` 是能力、成本和兼容性较平衡的选择，对标GPT-5.4、Claude Sonnet 4.6、Gemini 3 Pro：

- 支持中文文本理解，适合本项目的中文邮件查询问题；
- 具备编码和工具使用能力，适合生成 JOIN、聚合、子查询、日期处理和窗口函数等 SQL；
- 支持 Function Calling 和结构化输出，便于产品稳定提取 SQL；
- 上下文长度为100万 Token，能够容纳六张表的 Schema、字段注释、语义规则和用户问题；
- 使用固定快照，能够避免动态模型升级导致前后评测不可复现；
- 阿里云官方将 Qwen3.7 Plus定位为能力与成本均衡的推荐模型；在输入不超过256K时，官方列出的价格为输入2元/百万Token、输出8元/百万Token。

- [Qwen3.7 Plus模型信息](https://help.aliyun.com/zh/model-studio/qwen3-7-plus)
- [阿里云百炼文本模型选择指南](https://help.aliyun.com/zh/model-studio/text-generation-model)
- [阿里云百炼模型价格](https://help.aliyun.com/en/model-studio/model-pricing)

### 4. 为什么暂不选择其他模型

| 候选模型 | 暂不作为统一正式模型的原因 |
|---|---|
| `qwen3.7-max` | 推理能力更强，但本项目只有六张表，成本和时延增加未必带来同等收益 |
| `qwen3.6-plus` | 已验证接口可用，但属于上一代Plus模型，输出价格高于Qwen3.7 Plus |
| `qwen3.6-flash` | 成本和时延更低，可作为后续低成本对照，但复杂SQL准确率需要先验证 |
| `deepseek-v4-pro` | 编程和推理能力强，但思考输出、结构化输出和三产品兼容性需要额外验证 |
| `deepseek-v4-flash` | 适合速度和成本对照，但不能在未实测Enron问题前假定其NL2SQL准确率更高 |
| `qwen3-coder-plus` | 偏代码Agent，阿里云模型说明中未提供结构化输出能力，不作为当前首选 |

模型选型依据是工程适配和可复现性，不表示 Qwen3.7 Plus 已经在本项目上被证明准确率最高。正式50题运行前必须完成 Smoke Test。

同时需要在邮件问答知识库或Explore会话中确认实际模型也是 `qwen3.7-plus-2026-05-26`，不能继续使用历史批次中的 `deepseek-v4-flash`。

#### Chat2DB

### 6. 思考模式口径

思考模式会影响准确率、时延和Token，三个产品必须使用相同设置。

正式规则为：优先统一关闭思考模式，即请求参数使用 `enable_thinking=false`。如果Chat2DB当前版本不能设置该参数，则不能只在MOI或Wren中关闭；三款产品应统一使用阿里云接口默认模式，并在运行说明中记录为 `provider_default`。

在Smoke Test完成前，思考模式状态标记为“待确认”，不得开始正式50题计分。


### 8. 历史结果与新批次

历史结果继续保留：

| 产品或批次 | 历史生成模型 |
|---|---|
| MOI无语义配置 | `deepseek-v4-flash` |
| MOI有语义配置 | `deepseek-v4-flash` |
| Wren AI | `qwen-plus-2025-12-01` |
| Chat2DB | 底层模型未确认 |

新的统一模型评测应使用独立运行目录，例如：

```text
products/moi/results/qwen3.7-plus-2026-05-26/
products/wren/results/qwen3.7-plus-2026-05-26/

```

历史结果不能覆盖，也不能与新模型结果合并计算一个总准确率。

### 9. 密钥安全

- 仓库只记录环境变量名，不保存API Key值；
- MOI、Wren和Chat2DB使用本机私有配置；
- 已经出现在聊天、截图、终端记录或Git历史中的Key必须立即轮换；
- 公开提交前检查 `.env`、日志、截图和命令历史；
- 同一个公司Key可以用于三个产品，但需要关注并发限制和评测期间的其他业务流量。

## 模块二：评测题集设计与覆盖面

### 1. 题集构成

正式评测集包含50道中文自然语言问题。每道题都有稳定的题目ID、详细题意、Golden SQL和难度标签，三个产品必须使用同一份用户版问题文件进行评测。

| 维度 | 数量 | 占比 |
|---|---:|---:|
| 简单题 | 20 | 40% |
| 中等题 | 20 | 40% |
| 困难题 | 10 | 20% |
| 口语化问题 | 25 | 50% |
| 保留详细约束的问题 | 25 | 50% |
| 单业务表查询 | 34 | 68% |
| 跨业务表查询 | 16 | 32% |

这里的“跨业务表”按Golden SQL实际引用的六张Enron业务表统计，不把CTE、中间结果或子查询别名重复计算为新表。16道跨表题中，13道使用两张业务表，3道使用三张业务表。

### 2. 难度分层

难度不是只按SQL长度划分，而是综合考虑语义推断、表字段选择、连接关系、数据清洗和SQL结构。

| 难度 | 题目范围 | 主要能力 | 典型题目 |
|---|---|---|---|
| 简单 | `e01`—`e20` | 单表筛选、去重计数、关键词匹配、分组排序、Top N、基础日期解析，以及一题基础两表连接 | 邮件总数、回复邮件数、最常见邮箱文件夹、最近10封邮件 |
| 中等 | `m01`—`m20` | 跨表连接、一对多去重、平均值与百分比、日期分组、历史邮件头关联、缺失值处理和多来源表示比较 | 平均收件人数、回复过谁、标准To与X-To差异、2001年10月热门收件人 |
| 困难 | `h01`—`h10` | 集合交并差、反连接、多阶段CTE、主题标准化、分组内排名、窗口函数和复杂业务口径组合 | 双向通信地址、只发不收地址、最活跃主题、每人Top 3发件人、共同收件人 |

20/20/10的结构保证基础能力和组合能力都有足够样本，同时保留10道困难题区分产品处理复杂查询的上限。

### 3. 口语化与精确表达并存

50道题中有25道被改写为接近真实客户的问法，另外25道保留明确条件。口语化题在简单、中等、困难三个层级分别为10、10、5道，避免口语化程度与难度完全绑定。

口语化问题会隐藏表名、字段名、去重方式或SQL结构，例如：

- “Phillip Allen回复过谁的邮件最多？”要求模型理解“回复”对应当前回复邮件及 `enron_emailorig` 中 `nth=1` 的历史邮件头；
- “邮件往来最忙的是哪一天？那天发邮件最多的5个邮箱是谁？”要求模型先找出最忙日期，再进行第二阶段发件人排名；
- “每个人邮件最多的文件夹是哪个？并列的也都列出来。”要求模型理解按员工分组、保留并列第一，而不是全库只取一行。

详细问题则明确空值、大小写、去重、排序和并列处理等边界，用于检验产品在规则已经说清楚时能否严格遵循指令。两种表达共用同一套隐藏评测口径和Golden SQL，因此能够分别观察语义理解能力和精确指令执行能力。

### 4. 数据表与字段覆盖

题集覆盖Enron评测库的全部6张表和全部32个字段。这里的“覆盖”不是字段只出现在Schema中，而是题目要求在筛选、连接、分组、排序、计算或结果输出中实际使用。

| 表 | 主要业务含义 | 覆盖重点 |
|---|---|---|
| `enron_email` | 邮件归档目录 | 员工目录、邮箱文件夹、原始序号 |
| `enron_emailinfo` | 当前邮件主体与邮件头 | 日期、主题、发件人、To/X-To汇总文本、正文 |
| `enron_emailorig` | 正文中引用的历史邮件头 | 回复来源、上一层邮件、邮件链深度 |
| `enron_emailto` | 规范化标准收件地址明细 | 一对多收件人、收件地址去重、地址交集 |
| `enron_emailxto` | X-To原始显示值明细 | 原始收件人序号及其与标准To的表示差异 |
| `enron_source` | 数据来源元信息 | 来源员工、原始文件名、Lotus Notes文件夹 |

这种设计专门覆盖容易混淆的语义边界：归档员工不等于发件人、标准邮箱地址不等于原始显示名、当前邮件头不等于引用的历史邮件头、文件夹名称不等于数据来源目录。

### 5. SQL能力覆盖

题集覆盖的不只是简单检索，还包括以下可独立分析的能力类型：

- 基础查询：条件过滤、空值处理、去重、排序和Top N；
- 聚合分析：计数、平均值、百分比、最大值、分组统计和组内排名；
- 跨表查询：内连接、左连接、一对多关系和三表组合；
- 文本语义：正文关键词、回复主题识别、连续 `Re:` 前缀标准化和大小写归一化；
- 时间分析：解析原始Date邮件头，按年、月、日筛选或统计；
- 地址规范化：邮箱去除首尾空格、统一小写、同一邮件内去重；
- 集合关系：发件人与收件人交集、反连接、多人共同收件人和跨员工通信地址重叠；
- 高级SQL：CTE、条件聚合、子查询、`ROW_NUMBER`、`DENSE_RANK`及并列结果处理；
- 数据质量：NULL与空字符串、标准To与X-To表示差异、历史扩展邮件头字段完整性。

### 6. 全面性的边界

这50道题对当前Enron六表私有数据集具有较完整的覆盖：既覆盖全部表和字段，也同时考察自然语言歧义、业务语义映射、SQL生成和结果正确性。它适合比较MOI、Wren AI和Chat2DB在同一邮件分析场景下的NL2SQL能力。

但“全面”是针对本项目范围而言，并不代表覆盖所有数据库和SQL方言。当前题集不重点测试写操作、权限管理、事务、地理空间、JSON、递归查询或超大Schema检索；这些能力如需评测，应另建扩展题集，不能直接混入当前50题后继续沿用同一版本名称。

## 模块三：Chat2DB与Wren的NL2SQL流程及语义口径

### 1. 语义配置结论

Chat2DB和Wren本轮都没有导入为MOI单独制作的Enron规则JSON，也没有写入针对50道题的提示词、Golden SQL或问答样例，因此两者都属于“无额外业务规则注入”批次。

但两者不能笼统记为“完全没有语义信息”：

| 产品 | 本轮已有信息 | 未配置内容 | 评测标记 |
|---|---|---|---|
| Chat2DB | MySQL表名、字段类型、数据库中的表/字段注释；回答时按需读取Schema | 未导入独立语义模型、业务规则、表关系说明或Golden样例 | `no_extra_semantic_rules` |
| Wren AI | 导入六张表形成的模型、字段元数据及5条逻辑关系；Wren原生语义层和检索索引 | 未导入额外Enron业务规则、SQL Pair、历史问答或Golden样例 | `native_semantic_model_only` |

这里的差异必须保留：Wren的原生语义模型是产品工作机制的一部分，不应人为关闭；MOI后来导入的Enron规则JSON则属于额外语义增强，应作为单独批次报告。数据库原有注释属于共同Schema信息，不算针对某个产品的额外答案注入。

### 2. Chat2DB的NL2SQL逻辑

Chat2DB采用数据库工具型Agent流程，而不是把问题直接交给模型一次性生成SQL。根据本地实际日志，一次典型请求会经历：

1. 接收用户问题并识别当前连接的 `enron_eval` 数据库；
2. 调用表列表工具，选择可能相关的表；
3. 调用Schema工具，取得相关字段、类型和数据库注释；
4. 大模型根据问题和按需取得的Schema生成SQL；
5. 调用SQL执行工具；如果解析或执行报错，Agent可以继续修正并再次执行；
6. 根据执行结果生成最终自然语言回答。

因此Chat2DB的最终表现由模型、Agent提示词、选表与Schema探索、工具调用、错误修正共同决定。它不会默认把六张表的所有信息一次性塞给模型，而是由Agent在对话过程中决定查看哪些表。

### 3. Wren AI的NL2SQL逻辑

Wren采用较固定的语义检索与生成流水线：

1. 接收自然语言问题；
2. 从Wren语义模型及向量索引中检索相关表、字段、关系和可用说明；
3. 组合检索上下文，由大模型生成语义层SQL；
4. Wren Engine把语义模型引用展开为底层MySQL可执行SQL，生成结果中可能出现较长的CTE或嵌套查询；
5. 校验生成SQL；失败时进入SQL修正流程，配置允许时最多尝试3次；
6. 返回最终SQL和本次请求的线程标识。

Wren配置中包含Schema检索、历史问题检索、SQL Pair检索、指令检索、SQL生成和SQL修正等组件。本轮不提供历史问题、SQL Pair或额外指令作为答案提示，只保留Wren运行所必需的原生模型、字段和关系。

### 4. 对比边界

统一底层大模型并不等于绕开产品Agent直接调用模型。正式评测比较的是完整NL2SQL产品链路，其中包含各产品自己的Schema获取、语义层、提示词、规划、执行和修正能力。三个产品必须使用同一数据库快照、问题、生成模型和评分器，同时如实记录各自原生机制与额外语义注入情况。

## 模块四：本地部署、Docker与数据库端口排障

### 1. 本次问题的共同根因

Chat2DB和Wren都曾出现连接 `enron_eval` 失败或长时间等待的问题。根因并不是数据库不存在，也不是大模型无法生成SQL，而是本机3306端口在IPv4和IPv6上的实际监听对象不同：

- 真正的本地MySQL可以通过IPv6地址 `::1:3306` 访问；
- IPv4地址 `127.0.0.1:3306` 被VS Code的SSH端口转发占用；
- 因此把数据库地址笼统填写为 `localhost:3306` 或 `127.0.0.1:3306`，可能连接到错误的服务或一直超时。

这说明“都是本机3306端口”并不代表连接目标相同。排障时必须同时确认主机地址、IP协议、端口监听进程以及应用实际运行的位置。

### 2. Chat2DB的现象和解决方式

Chat2DB是直接运行在Mac上的桌面软件，与MySQL处于同一个主机网络环境。它的NL2SQL Agent也会读取Schema、生成SQL并连接数据库执行；连接问题并不意味着Chat2DB不会执行SQL。

原先使用 `127.0.0.1:3306` 时，连接落到了被SSH转发占用的IPv4端口。将连接地址明确改为 `::1`、端口保持 `3306` 后，Chat2DB可以直接访问真正的MySQL：

```text
Mac上的Chat2DB
    ↓
::1:3306
    ↓
本地MySQL / enron_eval
```

因为Chat2DB和MySQL都直接运行在Mac上，这里不需要额外的网络桥接。

### 3. Wren的现象和解决方式

Wren成功生成SQL后，还会通过Wren Engine/Ibis连接数据库进行预执行校验。故障发生时，大模型实际上已经生成了正确SQL，但数据库校验等待约30秒后超时，Wren最终将SQL判为无效并显示 `No relevant SQL`。因此该提示容易被误解为模型没有生成SQL，实际问题发生在生成后的数据库连接环节。

Wren的UI、AI Service、Engine、Ibis和Qdrant运行在Docker容器中。容器里的 `127.0.0.1` 或 `::1` 代表容器自身，并不代表外部的Mac，所以不能像Chat2DB一样直接填写Mac的 `::1:3306`。容器访问Mac需要使用 `host.docker.internal`。

由于Mac的IPv4 3306端口不能直接转到真正的IPv6 MySQL，本次增加了一个本机转发端口：

```text
Wren Docker容器
    ↓
host.docker.internal:13306
    ↓
本机数据库桥接 127.0.0.1:13306
    ↓
::1:3306
    ↓
本地MySQL / enron_eval
```

随后将Wren数据源端口从3306改为13306，并重启Wren UI、AI Service和Ibis以清理超时请求。修复后，SQL预检成功，试题“不同发件邮箱数量”生成的SQL实际返回836，与Golden结果一致。

数据库桥接脚本位于 `scripts/database/mysql_ipv4_proxy.py`。该桥接只转发网络连接，不复制或修改数据库数据；桥接进程停止后，Wren将再次无法通过13306访问MySQL，因此正式评测期间必须保持它运行。

### 4. 如何理解Docker

Docker可以近似理解为“运行在Mac中的轻量小主机”，但它不是完整虚拟机。它为应用提供相对独立的文件、依赖、进程、端口和网络环境，并通过镜像保证不同电脑上的部署尽量一致。

它与Python虚拟环境的区别是：`venv`主要隔离Python包，Docker则隔离整个应用运行环境，并且可以同时运行Python、Node.js、Java、数据库驱动等组件。对本项目而言，Docker使Wren的多个服务可以统一启动和复现，但网络隔离也意味着容器不能把自己的 `localhost` 当成Mac的 `localhost`。

可以使用下面的简化关系理解：

```text
Python venv = 独立的Python依赖工具箱
Docker容器 = 轻量、隔离的应用运行主机
虚拟机     = 包含完整操作系统的虚拟电脑
```

### 5. 本次排障结论

Chat2DB和Wren遇到的是同一类底层问题：真正的MySQL位于 `::1:3306`，而IPv4的3306端口被其他进程占用。两者解决方式不同，是因为Chat2DB直接运行在Mac上，而Wren运行在Docker隔离网络中：

| 产品 | 运行位置 | 最终连接方式 | 是否执行或校验SQL |
|---|---|---|---|
| Chat2DB | Mac本机 | 直接连接 `::1:3306` | 是 |
| Wren AI | Docker容器 | `host.docker.internal:13306`，再桥接至 `::1:3306` | 是 |

因此，在后续复现实验时，不能只记录数据库名和端口，还应记录产品运行位置、数据库主机地址、IPv4/IPv6协议、Docker到宿主机的访问方式及桥接进程状态。
