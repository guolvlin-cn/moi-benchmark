# MOI Enron NL2SQL 错误与提升分析

> 依据：同一模型 `qwen3.7-plus-2026-05-26`、同一50题、每题3轮；结合自动评测与人工审核。

## 1. 一页结论

| 指标 | 无语义配置 | 有语义配置 | 变化 |
|---|---:|---:|---:|
| 自动严格准确率 | 56.67% | 66.00% | +9.33个百分点 |
| 人工严格正确率 | 76.67% | **86.67%** | **+10个百分点** |
| 人工加权正确率 | 82.67% | **88.00%** | +5.33个百分点 |
| 三轮全部正确率 | 70.00% | **76.00%** | +6个百分点 |

结论：语义配置有效，尤其改善了“表和字段代表什么”“员工和邮箱如何对应”“如何计算邮件数”等问题。当前最应优先解决的不是继续堆大量规则，而是让 MOI **稳定命中并强制遵守已有语义规则**，再增加生成后的结果校验。

## 2. 本轮常见问题与改进方法

| 问题类型 | 典型题 | 为什么出错 | 建议如何提升 MOI |
|---|---|---|---|
| **语义理解/选错表** | `m10`、`m20`、`h08` | 模型按日常直觉选表，没有遵循业务定义。例如“回复过谁”误查当前收件人 `emailto.to`，而不是历史原邮件发件人 `emailorig.from` | 将高风险概念做成短而明确的“概念→表字段→SQL骨架”规则；生成前必须回显所选语义；生成后检查是否使用规定表字段 |
| **日期是字符串** | `e11`、`e12`、`h05` | 直接按 `date` 字符串排序或解析不稳定，导致 `Wed` 排在真正最新日期前 | 提供统一日期解析表达式/SQL模板；凡出现最新、年份、月份、最忙日期，校验器必须禁止直接 `ORDER BY date` |
| **计数粒度不对** | `m07`、`m13`、`m20` | `COUNT(*)` 被当成邮件数；分组前未 `TRIM`；归档记录数被当成不同邮件数 | 在语义层固定“一封邮件 = DISTINCT id”；地址、文件名、来源员工先规范化再分组；生成后检测计数粒度 |
| **输出列多或少** | `e16`、`m05`、`m06`、`h05` | SQL核心逻辑可能正确，但额外返回辅助列，或漏掉用户要求列 | 生成后增加“输出契约检查”：逐项比对用户要求的列，仅保留请求列；辅助列留在CTE中，不放最终SELECT |
| **回复/线程逻辑复杂** | `m10`、`h03` | 当前邮件、历史引用邮件、主题推断线程三种概念容易混淆 | 将三类任务拆成三个独立语义模板，不用一段长规则混写；`m10`直接提供带 `emailorig.nth=1` 的示例 |
| **跨引擎排序差异** | `e10`、`h02`、`h07` | SQL和结果集合正确，但MySQL与MatrixOne默认Collation不同 | 这不是MOI逻辑错误。评测器增加“同集合、仅顺序不同”标签；若业务必须顺序一致，在SQL中显式指定统一排序键/Collation |
| **超时和长尾** | `e03`、`h02`、`m17` | 3次超过300秒；P95升至173.25秒 | 优化Agent工具调用次数；SQL执行前估算复杂度；设置单步超时和一次快速重试；把超时与SQL错误分开统计 |

## 3. 最重点的语义错误：为什么“回复过谁”三轮全错

`m10` 问“Phillip Allen回复过谁的邮件最多”。三轮都查了：

```text
enron_emailto.to = Phillip回复邮件发给了谁
```

正确语义应该是：

```text
enron_emailorig.from = Phillip所回复的原邮件是谁发来的
并限定 enron_emailorig.nth = 1
```

现有语义配置已经写明这条规则，但三轮仍未遵循，说明问题不只是“缺少语义”，而是**规则检索或执行约束不够强**。

建议优先改为：

1. 将“回复过谁”单独做成高优先级短规则，不埋在长段落中。
2. 给出一条最小SQL示例：`emailinfo → emailorig ON id AND nth=1`。
3. 生成后自动检查：问题含“回复过谁/回复谁的邮件”时，SQL若未引用 `enron_emailorig`，直接要求Agent重写。

## 4. 语义配置为什么带来提升

本次语义配置主要补充了：

- 六张表各自的业务含义和连接关系；
- `people`、`xorigin`、`from`、`to`、`xfrom/xto` 的区别；
- Phillip Allen、Larry Campbell 与邮箱/归档所有者的映射；
- 一封邮件按 `DISTINCT id` 计数；
- RFC日期字符串必须解析后再排序或取年月日；
- 回复、历史邮件头和主题线程的区别；
- 地址、来源文件和来源员工的大小写及空格归一化；
- Top N、百分比和最终输出列的要求。

### 典型提升案例

| 题目 | 无语义时的问题 | 增加的关键语义 | 有语义后的表现 |
|---|---|---|---|
| `e05` Phillip Allen发件数 | 对人员对应邮箱范围理解不稳定 | Phillip Allen映射到 `phillip.allen@enron.com`，发件人用 `emailinfo.from` | 0.5/0.5/0.5 → **三轮全对** |
| `m01` 员工文件夹分布 | 混淆员工、来源员工和文件夹 | 归档员工用 `email.people`，文件夹用 `email.mailbox` | 仅部分轮次可用 → **三轮全对** |
| `m02` Phillip收件人 | 人员身份和收件明细映射不稳定 | 收件地址使用规范化 `emailto.to`，人员邮箱映射固定 | 0/1/0 → **三轮全对** |
| `m04` 来源员工文件夹 | 大小写导致同一员工/文件夹被拆分 | `xorigin`、`xfolder` 使用 `LOWER(TRIM())` | 三轮部分正确 → **三轮全对** |
| `m05` 平均收件人数 | 邮件粒度、收件人数和输出列不稳定 | 按邮件ID汇总收件人，再按发件人求平均 | 0.5/0/0.5 → **三轮全对** |
| `m12` 公告邮箱 | 自动扩展出多个“类似公告地址” | 公告邮箱固定为 `enron.announcements@enron.com`，禁止模糊扩展 | 两轮正确 → **三轮全对** |
| `h03` 回复主题线程 | 选错表或未完整去除连续 `Re:` | 当前邮件用 `emailinfo`；连续去除 `Re:` 后再小写分组 | 0.5/0/0 → **两轮全对** |
| `e11` 最近邮件 | 直接按日期字符串排序 | `date` 是RFC文本，必须 `STR_TO_DATE` 后排序 | 三轮错误 → 两轮部分、**一轮全对** |

语义配置提升最明显的地方是：**减少表映射和字段含义错误**。它不能完全消除模型随机性、超时和输出格式问题，因此仍需校验器与运行时优化配合。

## 5. 下一步改进优先级

### P0：先做，直接影响正确率

1. **语义命中强校验**：对 `m10` 这类高风险意图，检查SQL是否用了规定表字段；不符合就自动重写。
2. **输出列校验**：最终SELECT只返回用户要求列，减少“逻辑正确但列数不一致”。
3. **统一日期模板**：禁止对RFC日期原字符串做时间排序。
4. **统一计数模板**：用户说“邮件数”时默认 `COUNT(DISTINCT id)`。

### P1：提升稳定性和可评测性

1. 对超时增加一次受控重试，并记录是LLM慢、工具慢还是SQL慢。
2. 评测器将Collation差异标记为“跨引擎等价”，不混入NL2SQL逻辑错误。
3. 对自然语言歧义题（如 `h08`）在语义模型中明确唯一口径，或产品向用户发起澄清。

## 6. 最终判断

- 语义配置值得保留：人工严格正确率提升 **10个百分点**。
- 下一步不应只继续增加长文本规则；应把关键规则变成可检查的约束和SQL模板。
- 优先解决 `m10` 的历史回复语义、`h08` 的交集歧义、日期解析、邮件计数粒度和最终输出列。
- 排序Collation差异应由评测层单独处理，避免错误归因给MOI。
