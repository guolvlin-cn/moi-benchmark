# MOI NLP2SQL产品能力评测计划 v0.2：Spider Mix50

> 状态：已执行、已复盘
>
> 数据集：Spider dev mix50公开基准
>
> 参评产品：MOI、Wren AI、Chat2DB
>
> 主指标：Execution Accuracy
>
> 执行引擎：SQLite

## 1. 版本目标

v0.2 在 v0.1 的统一评测思想上，先使用公开 Spider 数据完成一个可复现的三产品横评，验证以下问题：

1. 三款产品面对相同问题和数据库时，能否生成执行结果正确的 SQL；
2. MOI 在单表、多表、聚合、子查询和集合运算上的基础能力如何；
3. 评测脚本、预测 SQL 对齐和结果等价比较是否可靠；
4. Spider 能覆盖哪些产品能力，不能覆盖哪些真实业务能力。

## 2. 范围与非目标

### 2.1 评测范围

- 从 Spider dev 1034 题中抽取 50 题；
- 覆盖 `concert_singer`、`car_1`、`pets_1` 三个数据库；
- 同时包含 easy、medium 和 hard；
- 对 MOI、Wren AI、Chat2DB 的最终 SQL 做统一离线执行；
- 保存预测 SQL、逐题记录、失败类型和汇总结果。

### 2.2 非目标

- 不把 Spider 结果解释为中文业务 NL2SQL 的完整能力；
- 不评价多轮澄清、图表、自然语言解释等端到端体验；
- 不把 SQL 文本完全一致作为正确标准；
- 不把不同产品的得分差异解释为纯模型能力差异；
- 不根据测试结果逐题修改 Prompt 后重算同一批正式成绩。

## 3. 测试集设计

### 3.1 题目构成

| 难度 | 题数 | 主要结构 |
|---|---:|---|
| Easy | 30 | 单表过滤、排序、聚合、Top-K |
| Medium | 15 | JOIN、GROUP BY、HAVING、多条件组合 |
| Hard | 5 | 子查询、EXCEPT、INTERSECT、复杂语义 |
| 合计 | 50 | 3个数据库 |

数据库分布：

| 数据库 | 表数 | 题数 | 主题 |
|---|---:|---:|---|
| `concert_singer` | 4 | 22 | 歌手、歌曲、演唱会、体育场 |
| `car_1` | 6 | 18 | 汽车、制造商、国家、洲、车型 |
| `pets_1` | 4 | 10 | 学生、宠物及拥有关系 |

### 3.2 冻结资产

- 问题：`spider/datasets/questions_mix50.txt`；
- Golden SQL：`spider/datasets/dev_gold_mix50.sql`；
- 题目顺序固定，预测 SQL 必须逐行对齐；
- 数据库使用 Spider 对应 SQLite 文件及官方 `tables.json`。

## 4. 参评产品与接入方式

| 产品 | 接入方式 | 方言或环境处理 |
|---|---|---|
| MOI | Explore API生成 SQL | 最终 SQL 在统一 SQLite 环境执行 |
| Wren AI | Cloud网页端逐题输入 | BigQuery方言中的 `SAFE_CAST`、`FLOAT64` 需记录并做明确适配 |
| Chat2DB | 桌面客户端 | 通过本地数据库连接取得 SQL，再离线评分 |

产品原生的 Schema 检索、SQL 修复和交互流程允许使用，但正式评测期间不得人工修改最终 SQL。

## 5. 公平性控制

1. 三款产品使用同一组问题、相同顺序和相同数据库内容；
2. Golden SQL 不进入产品上下文；
3. 所有预测 SQL 在同一个 SQLite 环境执行；
4. 方言转换只能做确定性的语法兼容，不得改变查询语义；
5. 重试、人工操作和异常必须保留记录；
6. 预测文件和 Golden 文件逐题对齐后才能评分；
7. 产品无法完成的题目保留空位，不得删除导致后续题号错位。

## 6. 执行协议

每个产品按以下流程运行：

1. 载入对应 Spider 数据库 Schema；
2. 新建或重置会话；
3. 输入一条问题并保存产品生成的最终 SQL；
4. 按原题顺序写入产品预测文件；
5. 使用 Spider test-suite 工具分别执行 Golden SQL 和预测 SQL；
6. 对比结果集并生成逐题报告；
7. 将错误区分为 SQL 语义、方言适配、数据类型、产品运行时或评测工具问题；
8. 完成全部题目后生成按难度和产品统计的报告。

## 7. 评分方法

### 7.1 主指标

Execution Accuracy：预测 SQL 与 Golden SQL 在相同 SQLite 数据库中的执行结果等价即判定通过。

运行参数：

```text
--etype exec --keep_distinct
```

使用 `keep_distinct` 是为了避免移除 `DISTINCT` 后对 `INTERSECT` 等集合运算产生误判。

### 7.2 诊断维度

- Easy、Medium、Hard 分项正确率；
- SQL 是否可执行；
- 表和字段选择；
- JOIN 路径与聚合粒度；
- 过滤、排序、Top-K 与返回范围；
- 多返列和少返列；
- 数据类型与方言兼容；
- 产品超时、连接错误和自动修复结果。

## 8. 结果等价与异常处理

- 主评判依据是执行结果，不比较 SQL 字符串；
- 结果顺序是否重要由查询语义和官方评测器决定；
- 数据库或评测器异常单独记录，不直接归因于 NLP2SQL；
- 生成了语法正确 SQL 但结果错误，仍判定为失败；
- 多返回辅助列在严格 Execution Accuracy 下判错，同时在失败分析中说明用户视角差异；
- Golden 存在歧义时记录为数据或评测限制，不静默修改历史结果。

## 9. 失败分类

```text
SCHEMA_LINKING
FIELD_SELECTION
JOIN_OR_AGGREGATION
FILTER_OR_RANGE
DATA_TYPE
DIALECT_ADAPTATION
EXTRA_OR_MISSING_COLUMNS
PRODUCT_RUNTIME
DATA_OR_GOLDEN
EVALUATOR_ALIGNMENT
UNKNOWN
```

## 10. 实施阶段

### Phase 0：工具验证

- 准备 Spider SQLite 数据库和 `tables.json`；
- 验证 test-suite 执行环境；
- 用 easy50 检查预测与 Golden 对齐；
- 修正 `remove_distinct` 等评测器使用问题。

### Phase 1：Mix50冻结

- 按 SQL 结构自动分类 Spider dev；
- 抽取 30 easy、15 medium、5 hard；
- 固定数据库和题目顺序；
- 执行 Golden SQL，确认样本可评分。

### Phase 2：三产品运行

- 分别生成 50 条预测 SQL；
- 保存原始预测和逐题运行记录；
- 统一执行并复核失败题；
- 生成三产品对比和典型案例。

## 11. 实际结果

| 产品 | Easy | Medium | Hard | 总计 |
|---|---:|---:|---:|---:|
| MOI | 22/30 | 8/15 | 3/5 | **33/50（66%）** |
| Wren AI | 26/30 | 10/15 | 5/5 | **41/50（82%）** |
| Chat2DB | 29/30 | 14/15 | 5/5 | **47/50（94%）** |

Spider 阶段暴露出的主要问题包括多返列、文本数值类型处理、回答范围偏差、复杂查询稳定性以及 Golden 歧义。

## 12. 交付物

- 50 道问题和 Golden SQL；
- 三产品预测 SQL；
- 三产品逐题执行报告；
- Spider test-suite 评测脚本；
- 难度分项和失败分类；
- Spider 阶段详细汇总报告。

所有交付物集中在 `nlp2sql/spider/`。

## 13. 局限与后续

Spider 是英文、单轮、给定 Schema 的学术数据集，无法充分测量中文业务术语、Schema 自主探索、字段注释利用、多轮澄清和端到端分析。v0.3 因此改用 Enron 邮件固定快照和中文问题，并增加语义配置实验。
