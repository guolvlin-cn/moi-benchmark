# MOI NLP2SQL评测计划 v0.4：多维指标与可观测性扩展

> 状态：后续实施计划
>
> 基线：Enron Eval 50 v1
>
> 目标：在 Execution Accuracy 之外补齐回答、可靠性、时延、Token、成本和可运维性指标
>
> 原则：质量、性能和成本分开报告，不计算单一加权总分

## 1. 为什么需要v0.4

v0.2 Spider 和 v0.3 Enron 的主指标都是 Execution Accuracy。这个指标回答了“最终 SQL 的执行结果是否正确”，但不能完整回答：

- 产品是否稳定生成 SQL；
- 第一次是否正确，还是依靠多轮修复才正确；
- 最终自然语言回答是否忠实于 SQL 结果；
- 用户需要等待多久；
- 每题消耗多少 Token、模型调用和费用；
- 同一道题重复运行时是否稳定；
- 配置语义层、连接数据库和人工干预需要多少成本。

RAG 评测中的分层报告、P50/P95、Token、成本、运行完整性和失败留在分母等思想可以复用；Recall@K、MRR、Citation Precision 等检索专用指标不直接迁移到 NL2SQL。

## 2. 指标体系总览

| 层级 | 核心问题 | P0必报指标 | P1扩展指标 |
|---|---|---|---|
| 结果正确性 | 查出的数据对不对 | Execution Accuracy | 分能力和分题型准确率 |
| SQL有效性 | 能否安全生成并执行 | SQL Generation、Safe SQL、Executable Rate | First-pass、Repair Recovery |
| 回答质量 | 给用户的回答是否正确有用 | Answer-SQL Consistency | Completeness、Usefulness、Clarification |
| 可靠性 | 是否稳定完成请求 | Availability、Timeout/Error Rate | 重复一致率、Flip Rate、Pass@k |
| 时延 | 用户要等多久 | E2E P50/P95 | 首条SQL、SQL执行、修复耗时 |
| Token与成本 | 正确答案代价多大 | Input/Output/Total Tokens | Cost/Question、Cost/Correct |
| 可运维性 | 产品接入和维护难不难 | 配置时间、人工干预数 | Schema同步、语义维护和审计完整率 |

## 3. P0核心质量指标

### 3.1 Execution Accuracy

```text
执行结果正确题数 / planned initial questions
```

继续作为主质量指标。失败、超时、空 SQL 和未开始题目不能从分母删除。

### 3.2 SQL Generation Rate

```text
生成非空候选SQL的题数 / planned initial questions
```

只表示“生成了 SQL”，不能替代正确率。

### 3.3 Safe SQL Rate

```text
通过只读安全检查的候选SQL数 / 生成非空SQL数
```

只允许单条 `SELECT` 或只读 CTE。DDL、DML、事务控制、文件读写、多语句和越权表访问均判失败。

### 3.4 Executable Rate

```text
在目标数据库成功执行的候选SQL数 / 通过安全检查的候选SQL数
```

SQL 可执行不等于结果正确，因此必须与 Execution Accuracy 分列。

### 3.5 First-pass Accuracy

```text
第一次生成且未经自动修复即执行正确的题数 / planned initial questions
```

用于区分模型首次能力和产品修复能力。

### 3.6 Final Accuracy

```text
在冻结的最大重试与修复预算内最终正确的题数 / planned initial questions
```

必须同时报告 First-pass 和 Final，不能只展示修复后的最好结果。

### 3.7 Repair Recovery Rate

```text
首次失败但最终修复正确的题数 / 触发修复且首次失败的题数
```

同时报告修复导致“原本正确变错误”的回归数量。

## 4. 端到端回答质量

NL2SQL 产品往往不只返回 SQL，还返回数字、表格和解释。SQL 正确但自然语言总结错误，用户仍会收到错误答案。

### 4.1 Answer-SQL Consistency

检查回答中的数字、实体、排序、Top-K 和结论是否与实际 SQL 执行结果一致。

建议每题二元判定：

```text
1 = 回答与执行结果无矛盾
0 = 存在错误数字、遗漏关键限定、错误排序或虚构结论
N/A = 产品不生成自然语言回答
```

### 4.2 Answer Completeness

根据问题要求的返回列和关键事实，统计完整覆盖率：

```text
完整回答的必需输出项 / 问题要求的全部输出项
```

多返有用信息不自动扣分，但不得替代问题要求的核心输出。

### 4.3 Answer Usefulness

人工采用 1–5 分量表，单独报告，不进入严格正确率：

- 1：无法使用或明显误导；
- 3：核心信息可用，但表达或结构一般；
- 5：准确、简洁、列名清楚，便于用户继续分析。

至少抽取失败题、复杂题和产品分歧题进行双人盲审。

### 4.4 Clarification与Correct Abstention

后续新增歧义题和不可回答题时报告：

- Clarification Success：应澄清时是否提出有效问题；
- Correct Abstention：数据不足、越权或无法回答时是否正确拒答；
- Wrong Confident Answer：不应回答却自信生成结果的比例。

## 5. 可靠性与稳定性

### 5.1 Run Completeness与Availability

```text
Run Completeness = 已对账的终态initial attempts / planned initial attempts

Availability = 未发生连接、产品运行时或超时错误的initial attempts / planned initial attempts
```

终态包括成功、明确产品错误和超时。Run Completeness 衡量运行账本是否完整；Availability 衡量产品是否实际可用，两者不能混用。未对账请求不能算成功。

### 5.2 Error与Timeout

分别报告：

- HTTP或连接错误率；
- LLM超时率；
- SQL生成错误率；
- 数据库执行超时率；
- 解析或提取 SQL 失败率。

### 5.3 重复稳定性

从 50 题中冻结 15 题稳定性子集，覆盖 Easy 5、Medium 6、Hard 4，每个产品独立运行 3 次。

报告：

- Pass/Pass Consistency：三次均正确；
- Fail/Fail Consistency：三次均失败；
- Flip Rate：同题不同运行在正确与错误之间翻转；
- Pass@1 与 Pass@3；
- SQL结构一致率和结果一致率。

不得从三次结果中挑最好一次替代正式 initial 分数。

## 6. 时延指标

### 6.1 必报时延

| 指标 | 起止点 |
|---|---|
| End-to-end latency | 提交问题到收到最终可展示回答 |
| SQL generation latency | 提交问题到获得首条候选SQL |
| SQL execution latency | 数据库开始执行到结果读取完成 |
| Repair latency | 首次失败到最终修复结束 |

每项至少报告：`count`、mean、P50、P95、max、timeout count。

### 6.2 统计规则

- warm-up 请求与正式请求分开；
- 成功、失败和超时分别报告；
- timeout 不能从请求分母删除；
- 产品起止点不一致时标记 `NOT_COMPARABLE`，不能直接排行；
- Chat2DB 等手工产品无法取得精确服务端时延时记 `N/A`，不能填 0；
- 第一轮先测单并发，吞吐与并发性能作为后续独立实验。

### 6.3 当前可恢复的描述性时延

现有 Enron 运行文件已经保存 MOI 与 Wren 的逐题时延。按当前字段直接汇总：

| 批次 | N | Mean | P50 | P95 | Max |
|---|---:|---:|---:|---:|---:|
| MOI无语义 | 50 | 34.731s | 24.682s | 112.693s | 145.651s |
| MOI有语义 | 50 | 22.896s | 17.988s | 44.031s | 62.814s |
| Wren本地 | 50 | 19.992s | 19.243s | 34.520s | 34.733s |
| Chat2DB | 50 | N/A | N/A | N/A | N/A |

这些数据的计时起止点和产品运行方式尚未完全统一，只能作为描述性历史记录，不能据此发布正式速度排名。

## 7. Token与成本指标

### 7.1 每次请求必采字段

- `input_tokens`：问题、Schema、语义配置和历史上下文消耗；
- `output_tokens`：SQL、解释和修复输出；
- `total_tokens`；
- `llm_call_count`；
- `tool_call_count`；
- `repair_count`；
- `cached_input_tokens`，若平台可提供；
- `estimated_cost` 与货币单位；
- `pricing_snapshot_id`，记录当时模型单价。

### 7.2 汇总指标

- Mean/P50/P95 input、output、total tokens；
- 模型调用次数/题；
- Token/Correct Question；
- Cost/Question；
- Cost/Correct Question；
- 语义配置前后 Token 和成本差异；
- 失败请求消耗的 Token 和费用。

平台不暴露 Token 时记 `N/A: USAGE_UNAVAILABLE`，不能使用字符数冒充官方 Token。可以另报估算值，但字段名必须为 `estimated_tokens`。

## 8. 可运维性指标

每个产品记录：

- 首次数据库接入耗时；
- Schema 同步或知识库构建耗时；
- 语义配置耗时和规则数量；
- 50 题运行所需人工分钟数；
- 人工点击、复制、重试和修复次数；
- 需要管理员权限的步骤数；
- 可导出的 SQL、错误、Token 和调用轨迹覆盖率；
- 产品升级后重新配置时间。

这些指标单独形成 Operability 表，不与正确率加权。

## 9. 诊断切片

所有核心指标至少按以下维度切片：

- Easy、Medium、Hard；
- 口语化与精确问题；
- 单表、多表 JOIN、聚合、日期、文本、集合、窗口函数；
- 涉及表数量；
- 是否使用保留字字段；
- 是否需要地址或线程规范化；
- 产品、模型、语义配置和运行批次。

小切片必须同时显示题数，避免用 1–2 题的百分比得出泛化结论。

## 10. 统计与比较

- 所有比例同时报告 numerator/denominator；
- 50题总体率报告 Wilson 95%置信区间；
- 同一问题上的两产品正确/错误差异使用 McNemar 检验；
- 重复运行使用按 `question_id` 聚类的 bootstrap；
- 缺失值必须带原因，不用 0 代替；
- 环境失败和产品失败分列，但都保留在运行账本；
- 不将正确率、时延和成本压缩成一个综合分。

## 11. 建议的端到端任务成功门槛

可以增加每次 attempt 的二元 `E2E Task Success`，用于回答“用户这次任务是否真正完成”：

```text
safe_sql
AND executable
AND execution_result_correct
AND answer_sql_consistent（产品有自然语言回答时）
AND no_timeout_or_product_error
```

它是质量门槛，不包含时延、Token 或价格。性能和成本继续独立报告。

## 12. 运行数据合同

每次请求保存一行 JSONL：

```json
{
  "question_id": "m03_top_sender_addresses",
  "repeat_id": 1,
  "attempt_kind": "initial",
  "product": "moi",
  "run_id": "2026-xx-xx_moi_v04",
  "status": "ok",
  "generated_sql": "SELECT ...",
  "raw_answer": "...",
  "timing": {
    "end_to_end_ms": 18000,
    "sql_generation_ms": 15000,
    "sql_execution_ms": 120,
    "repair_ms": 0
  },
  "usage": {
    "input_tokens": 5000,
    "output_tokens": 600,
    "total_tokens": 5600,
    "llm_call_count": 2,
    "tool_call_count": 3,

    "estimated_cost": 0.012,

  },

```

评分结果单独保存，不能回写或覆盖产品原始输出。

## 13. 最小实施顺序

### Phase A：统一采集，优先级P0

1. 扩展 MOI、Wren Adapter 的 timing 和 usage 字段；
2. 为 Chat2DB 设计手工计时表，Token 不可见时保持 N/A；
3. 统一 initial/retry/repair 状态；
4. 扩展评分器输出 SQL Generation、Safe、Executable、First-pass、Final；
5. 汇总 P50/P95、错误率和 Token/成本。

### Phase B：回答与稳定性，优先级P1

1. 为 50 题补充 `expected_columns` 和必需回答项；
2. 对自然语言回答做 SQL-result consistency 检查；
3. 冻结 15 题稳定性子集，每题运行 3 次；
4. 输出 Flip Rate、Pass@k 和 Repair Recovery；
5. 双人盲审回答完整性与有用性抽样。

### Phase C：性能与鲁棒性，优先级P2

1. 增加同义改写、列名干扰、Schema扩大和空结果变体；
2. 固定硬件、并发、warm-up 和 timeout；
3. 分别发布质量报告与性能附录；
4. 只有单并发质量门槛通过后才进行吞吐或并发测试。

## 14. v0.4交付物

- 新版 attempt JSONL schema；
- MOI、Wren、Chat2DB 采集字段映射表；
- 多维评分器与指标单元测试；
- 运行分母账本；
- 质量、可靠性、时延、Token、成本和可运维性六层报告；
- 15题×3次稳定性报告；
- 失败案例和人工回答质量复核表；
- 指标缺失原因和不可比变量说明。
