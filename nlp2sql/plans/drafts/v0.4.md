# MOI NLP2SQL评测计划 v0.4：Enron四项指标增量评测

> 状态：计划中
>
> 基线：Enron Eval 50 v1
>
> 正式产品：MOI、Wren AI、Chat2DB
>
> 可选产品：阿里云 Data Agent，完成核心三产品后视时间和接入条件决定

## 1. 目标与范围

v0.4 不更换 Enron 数据快照、50 道问题和 Golden SQL，只在 v0.3 的 Execution Accuracy 基础上增加少量可直接计算的指标。

本版不依赖产品内部的初次生成、自动修复、Token 或调用轨迹。每道题只需取得：

- 最终生成 SQL；
- 从提交问题到完整返回的外部计时；
- 最终 SQL 在统一 MySQL 8 数据快照上的执行结果；
- Golden SQL 在同一快照上的执行结果。

自然语言回答质量、Token、成本、人工操作体验和内部修复过程不进入 v0.4 正式指标。原因是三个产品无法稳定提供同口径数据，强行比较会造成不公平。

## 2. 指标体系总览

本版只保留四项正式指标。

| 指标 | 计算公式 | 回答的问题 |
|---|---|---|
| Execution Accuracy | `结果与Golden一致的题数 / 50` | 最终查询结果是否正确 |
| SQL Success Rate | `生成非空、安全且成功执行SQL的题数 / 50` | 产品能否稳定交付可运行SQL |
| End-to-end Latency | 完成请求耗时的 `P50`、`P95` | 普通请求和慢请求需要等待多久 |
| Repeat Correct Rate | `重复3次均正确的题数 / 10` | 同一问题重复提问时是否稳定正确 |

所有比例必须同时报告分子和分母，例如 `41/50（82%）`，不能只写百分比。

## 3. 具体测量方法

### 3.1 Execution Accuracy

对每道题执行：

1. 在统一 MySQL 8 Enron 快照执行产品最终生成的 SQL；
2. 在同一数据库执行对应 Golden SQL；
3. 对两个结果集做相同的规范化；
4. 规范化后完全相等记 `is_correct=true`，否则为 `false`。

```text
Execution Accuracy = count(is_correct=true) / 50
```

结果规范化继续沿用 v0.3 口径：

- 统一 NULL 表示；
- 统一整数、浮点数和 Decimal 的可比格式；
- 清理字符串尾部空格；
- 列数量和列值必须一致；
- 问题要求排序时保持行序比较；
- 问题未要求排序时按规范化后的整行排序再比较。

没有生成 SQL、SQL 不安全、执行报错或超时的题目都记为错误，仍保留在50题分母中。

### 3.2 SQL Success Rate

一道题必须同时满足以下三个条件才算 SQL 成功：

```text
generated_sql非空
AND safe_sql=true
AND execution_status=success
```

```text
SQL Success Rate = 满足以上三个条件的题数 / 50
```

安全检查只允许单条只读 `SELECT` 或只读 CTE。出现 `INSERT`、`UPDATE`、`DELETE`、DDL、事务控制、文件读写、多语句或越权访问时，`safe_sql=false`，不得执行。

失败原因只作为诊断计数，不增加新的正式指标：

```text
no_sql
unsafe_sql
sql_parse_error
db_execution_error
timeout
product_error
```

每道题只记录一个主失败原因。

### 3.3 End-to-end Latency

统一使用外部计时：

```text
started_at = 问题提交完成的时间
ended_at   = 最终回答和SQL完整返回的时间
latency_ms = ended_at - started_at
```

将有完整起止时间且未超时的请求按 `latency_ms` 从小到大排列。设有效数量为 `n`：

```text
P50 = 第 ceil(0.50 × n) 个值
P95 = 第 ceil(0.95 × n) 个值
```

报告格式固定为：

```text
n、P50、P95、Max、Timeout Count
```

超时阈值在运行前冻结，超时请求不进入 P50/P95 数值计算，但必须报告 `Timeout Count`，并在 SQL Success Rate 中计为失败。

如果某产品只能取得人工计时，必须标记 `MANUAL_TIMING`；如果无法取得相同起止点，记 `N/A: TIMING_NOT_COMPARABLE`，不能填0。

### 3.4 Repeat Correct Rate

从50题中预先冻结10题，覆盖：

- Easy 3题；
- Medium 4题；
- Hard 3题；
- 单表、JOIN、聚合、日期和文本条件均至少出现1题。

每个产品对这10题各独立运行3次，每次使用新会话且不保留上一轮上下文。每一次仍按照 Execution Accuracy 的方法评分。

```text
Repeat Correct Rate
= 3次运行全部is_correct=true的题数 / 10
```

例如某题三次结果为“正确、错误、正确”，该题不计入分子。三次结果完全相同但都错误，也不计入分子。

Chat2DB 如果只能人工运行，也按照相同10题×3次执行；无法完成时该指标记 `N/A: REPEAT_RUN_UNAVAILABLE`，不使用单次结果代替。

## 4. 最小数据字段

每次请求保存一行 JSONL，只要求以下字段：

```json
{
  "question_id": "m03_california_senders",
  "product": "moi",
  "run_id": "2026-xx-xx_moi_v04",
  "repeat_id": 1,
  "generated_sql": "SELECT ...",
  "status": "ok",
  "started_at": "2026-xx-xxT10:00:00.000+08:00",
  "ended_at": "2026-xx-xxT10:00:18.000+08:00",
  "latency_ms": 18000,
  "safe_sql": true,
  "execution_status": "success",
  "is_correct": true,
  "error_type": null
}
```

不要求 `initial_result`、`final_result`、Token、成本或产品内部修复记录。评分程序可以在运行时执行最终 SQL 和 Golden SQL，得到 `is_correct`，不需要把完整结果集长期写入 JSONL。

## 5. 评测步骤

### Phase A：冻结条件

1. 校验50个 `question_id`、问题、Golden SQL 和难度标签；
2. 冻结数据库快照、产品版本、模型、语义配置和超时阈值；
3. 冻结10道稳定性题目；
4. 每个产品先运行2道不计分 warm-up。

### Phase B：运行50题

1. 每道题使用独立会话；
2. 外部记录 `started_at` 和 `ended_at`；
3. 保存产品最终生成 SQL，不人工修改；
4. 未生成、报错和超时也必须保存一行记录；
5. 在统一 MySQL 8 快照执行候选 SQL 和 Golden SQL。

### Phase C：稳定性复测

1. 对冻结的10题各运行3次；
2. 每次重新建立会话；
3. 分别计算每次 `is_correct`；
4. 汇总 Repeat Correct Rate。

### Phase D：生成报告

每个产品只生成下面的主表：

| 产品 | Execution Accuracy | SQL Success Rate | P50 | P95 | Timeout | Repeat Correct Rate |
|---|---:|---:|---:|---:|---:|---:|
| MOI | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| Wren AI | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |
| Chat2DB | 待测 | 待测 | 待测 | 待测 | 待测 | 待测 |

此外保留逐题记录和失败原因计数，用于解释分数，但不再创建复杂综合评分。

## 6. 可选竞品：阿里云 Data Agent

完成核心三产品后，如仍有时间，先验证阿里云 Data Agent：

1. 能否连接或导入 Enron 数据；
2. 能否输出最终 SQL；
3. 能否完成5道 Smoke Test；
4. 能否按照相同方式取得外部耗时；
5. 数据上传和账号权限是否符合要求。

全部通过后，再使用相同50题、10道稳定性题和四项指标。具体产品版本未确认前，不进入主报告。

## 7. 交付物

- 四项指标计算脚本；
- 三产品各50题的最终 SQL 与逐题评分；
- 三产品各10题×3次的稳定性记录；
- P50/P95 时延汇总；
- 失败原因计数；
- 更新后的 Enron 产品对比报告；
- 更新后的顶层 NL2SQL 汇总报告；
- 如完成阿里云 Data Agent，增加独立附录。

## 8. 完成标准

- 三个产品各有完整50题记录；
- 所有失败和超时保留在分母；
- 四项指标均能由脚本重新计算；
- 10道稳定性题已完成3次独立运行，或明确记录产品无法重复运行的原因；
- 计时方式和不可比项已披露；
- 原始 SQL、逐题评分和汇总结果可以通过 `question_id` 对账。
