# MOI RAG 产品级 Benchmark 计划 v0.3

> 日期：2026-07-29 ｜ 状态：Draft ｜ supersedes：`v0.2.md`

本文件是可执行的产品级协议草案。正式运行前冻结所有阈值、字段、配置、门禁、无效运行规则和报告模板。本计划不生成加权总分、排行榜或“总体赢家”。

## 1. 身份、目标与边界

### 1.1 身份门禁

本计划中的 MOI 指 **MatrixOne Intelligence**。正式执行前记录身份确认、部署形态、前端/后端构建版本、租户、区域、权限/Entitlement 和日期；身份或部署不明确则停止，不以产品别名替代确认。

### 1.2 原生边界

产品级目标是同一批原始文件在各产品自身路径上的可复现 Data-to-Answer 体验：

`raw file load → product-native parsing/chunking/embedding → searchable artifacts/jobs → native Explore retrieval/answer`。

MOI 的 Native 结果只来自原生工作流和原生 Explore（或经批准的等价 Native API）。MOI→Dify、MOI+DeerFlow/MCP 等导出/集成路径永不计入 MOI Native。MOI、Dify、FastGPT 各自从同一原始文件开始，使用各自原生路径；RAGFlow 延后。

### 1.3 赛道

- **Quick-start Native**：采用官方推荐默认或模板；多个推荐项按预注册用户画像和固定 tie-break 选择。冻结 onboarding/support 脚本、支持预算和时间窗口，测量 time-to-value。
- **Frozen Optimized Native**：仅在 dev split 调优；每产品同时冻结相同最大 dev trials、active person-hours、wall-clock window、配置动作数、allowed search space、stop rule 和 vendor-help 是否计时。hidden 不可访问或选择。
- **Controlled Generation（可选诊断）**：外部统一 generator 接收标准化 `retrieved-context envelope`；固定排序、拼接、截断、context token budget、citation schema，以及完全相同 model/version、system+user template、temperature、max output。不能导出真实 context/trace 的系统标为 unavailable，不得部分控制或从答案反推；与 Native 完全隔离，永不混合或替代 Native 结果。

两种 Native 条件不得混报。任何不满足条件的配置标记为不可比或缺失能力。

## 2. 北极星与测量原则

### 2.1 Trusted Data-to-Answer Success（TDAS）

TDAS 是产品的北极星，而非模型准确率。可回答题的一次请求只有同时满足以下条件才成功：

1. 题目所有 required reference claims 各至少有一套 complete alternative evidence set，且该集合全部 ready/searchable；
2. initial request 成功；
3. `Correctness ≥ 0.8`；
4. `Reference-claim Recall ≥ 0.8`；
5. `Gold-evidence Support = 1`；
6. 无 critical contradiction；
7. 对 citation-required answerable 题，`Citation Precision = 1` 且 `Required Claim Citation Coverage = 1`。

不可回答题成功须 initial request 成功、明确拒答或证据不足声明与题目原因一致、不得输出无证据事实或伪造引用；允许纠正错误前提，但不得加入无支持事实。可回答题错误拒答单独计入 false refusal。

可选 `SLO-TDAS` 在 TDAS 上增加 formal run 前冻结的 latency、availability、cost 上限；未达到 SLO 不能被质量分掩盖。

TDAS 最小计分单元是 `(system_id, native_condition, question_id, repeat_id)`。每个冻结 hidden/formal question 的三次 scored initial attempt 全部进入分母；所需 Gold source/evidence 未 accepted/ready/searchable、query/API/product failure、必需引用缺失均 TDAS=0，并保留对应 stage failure。只有预注册 Gold/dataset defect 可触发对所有系统共同生效的 `question_invalid`；单次 benchmark-side fault 按第 8 节的 `run_invalid` 和 replacement 规则处理；不得因产品结果按系统删题。TDAS 只作为布尔任务成功率和分层摘要，不创建 weighted total/overall champion。所有 component metrics、样本量、缺失能力和置信区间均单独报告。

### 2.2 规范 metric/判分合同

| 指标 | Numerator / denominator | Eligible set、空集、边界与例外 |
|---|---|---|
| Correctness | `Σ correctness_label_score(c) / |eligible canonical factual response claims|` | `correct=1`、`partially_correct=0.5`、`incorrect=0`；answerable 分母空=0。重复/同义 claims 先 canonicalize 去重；boilerplate/non-factual 排除但保存。 |
| Reference-claim Recall | 被响应**语义正确覆盖**的 required reference claims / required reference claims | coverage 为二元：完整语义覆盖=1，部分覆盖=0。alternative evidence sets 只确认该覆盖存在 Gold 支持，不是检索命中或 recall 判据；required 集合为空则该指标 N/A，不可回答题不套用。 |
| Gold-evidence Support | 完全由任一有效 Gold evidence set 支持的 eligible response factual claims / eligible response factual claims | answerable 空答案或拒答=0；分母为空则=0。只计完整支持，不把 runtime context faithfulness 替代 Gold support。 |
| Citation Precision | 支持对应 claim 的 valid citations / all submitted claim citations | valid 必须 source/hash/page/span 对得上、支持所关联 claim 且在 selected-file scope 内；任何伪造、越 scope、错误 source/page/span/hash 的引用令 Precision<1；提交集合为空时 precision=1，但 required coverage 仍可为 0。 |
| Required Claim Citation Coverage | 有至少一条 valid citation 的 required/citation-required response claims / 需要 citation 的 response claims | 需 citation 集合为空则 N/A；TDAS 需要的引用缺失/无效即 TDAS=0。 |
| Critical contradiction | 直接冲突的响应 claims 数及 TDAS gate | 与任一 required Gold claim、数值、实体、版本或约束直接冲突且改变答案即 critical；存在即失败。 |
| Unanswerable success | 严格正确拒答（或证据不足声明）且无无支持事实/伪造 citation的单独布尔规则 | 不套 answerable 指标；false refusal 在 answerable cohort 单独报告。 |

所有分数按预注册 rounding 计算，所有 `≥` 边界含等号。对非 citation-required 题，无 citation 不导致 TDAS 失败；但伪造/错误引用仍作为对应 claim 错误或风险单报。响应 claim canonicalization 的映射、partial support、duplicate/同义处理、拒答和空集合结果随 raw judge 输出保存。

### 2.3 五层产品旅程

| 层 | Track | 关注内容 |
|---|---|---|
| A | Data Readiness | 文件接收、解析/构建、嵌入、可搜索就绪、证据保存与来源映射 |
| B | Evidence Retrieval & Scope | 证据召回、完整证据集、排序（有真实 trace 时）、选中文件隔离 |
| C | Native Answer & Citation | 正确性、reference-claim recall、gold support、拒答、引用 |
| D | Reliability/Performance | 初次成功、重试诊断、时延、成本、稳定性 |
| E | Product Operability | 可观察性、配置、作业状态、诊断、恢复、时间/动作成本 |

所有层在一次 native journey 中串联；E 层作为描述性产品证据，不能折入答案分。

## 3. 用户旅程与可观察输出

### 3.1 旅程定义

1. **Identity/deployment freeze**：确认身份、版本、租户、资源与 entitlements；输出签名 manifest。
2. **Admin ingestion**：管理员加载 corpus、创建/运行原生知识库或 workflow；开始于第一项配置动作，结束于 ready criterion 满足或明确失败。
3. **Operator observation/recovery**：观察 job、artifact、告警、自然发生的失败和重试，按固定 runbook 处理；自然故障仅作 observational。另运行预注册、各产品等同的 fault-injection/recovery scenarios（仅当产品/环境安全允许），输出状态时间线、动作、诊断、重试与恢复结果。
4. **Analyst query**：新鲜 session 中进行单文档、多文档、exact identifier、版本/干扰、不可回答题；开始于请求提交，结束于首个响应或明确 API/UI failure。
5. **Auditor verification**：核对 source/page/span/bbox/hash、用户可见 citation、lineage 与选中文件 scope；输出审计表和争议项。
6. **Reset/rebuild**：作为独立 diagnostic run 重置或重建代表性子集；恢复到 manifest 签名状态并经 hash 校验后才能继续 formal query，不得污染正式分数；输出前后 hash、耗时和差异。

每一步记录起止时间、人员角色、动作数、人工分钟、配置错误、状态/诊断质量、可恢复性和最终 artifacts。固定 runbook 与 operator onboarding；不同系统使用同等支持预算，结果分开呈现。fault-injection 冻结 event definition、severity/rubric、观察窗、终止条件和 censoring 规则。

### 3.2 产品可运维指标

报告 `Time-to-First-Searchable-Corpus`、`Time-to-First-Trusted-Answer`、active human minutes、elapsed time、action/intervention count、configuration error count、status/diagnostic quality、recoverability，以及 build/query latency 和成本。配置错误定义为阻止/改变预期流程的用户配置动作错误；diagnostic quality 按预注册 rubric（准确、及时、可操作）分级；recoverability 按自动恢复、runbook 一步恢复、需重建、不可恢复分级。不要将这些指标折算为 TDAS。

## 4. Corpus、fresh-control 与数据集

### 4.1 现有 baseline

保留当前观测的 46 PDF（约 58 MiB、约 1,104 页，主要为英文技术/硬件文档）为 `public_baseline`。最终 manifest 重新核验数量、页数、hash、语言、授权、egress 和安全；pre-freeze 观察不得当作最终结论。

### 4.2 必需 fresh-control

先做 Smoke：30–50 题、覆盖 10–15 个代表性 document families，用于发现解析、adapter、judge 和 artifact 问题；通过门禁后才冻结 formal set。正式 run 前新增 8–12 份新撰写的、private-or-fictional 但真实感的、有版本标识的 PDF；必须 egress-safe。为该 slice 生成 30–40 个 hidden questions，降低参数记忆混淆。fresh-control 计入正式 hidden formal 总量且单独报告。

dev corpus/questions 另行构建并仅用于配置与 judge 开发；正式总量 180–240 题明确指 hidden formal scored questions（包含 fresh-control），沿用互斥配额：

| 类型 | 比例 |
|---|---:|
| 单文档、单证据 | 35% |
| 单文档、多证据 | 20% |
| 跨文档证据链 | 15% |
| 表格/视觉条件 | 10% |
| 不可回答 | 20% |

正交标签包括 `exact_identifier`、`semantic_paraphrase`、`distractor`、`version_disambiguation`、`long_document`、`query_language`、`fresh_control`。全量证据先行生成，绝不使用产品输出产生 Gold。按 document family/near-duplicate connected component 做 20/80 dev/hidden split；`question_family_id`、paired variants 和 `analysis_cluster_id` 不得跨 split。Smoke 不进入 hidden 分数，除非冻结时明确转为正式题并重新锁定 lineage。

### 4.3 Manifest 与 lineage

文件 manifest 至少包含 `dataset_id`、`id`、`path`、`sha256`、`bytes`、`pages`、`language`、`domain`、`document_family`、`version`、`parseability`、`table_image`、`sensitivity`、`egress`、`license`、split、访问级别、保留期和生成代码版本。

题目 schema 延续 v0.2 的 `question_id`、`base_question_id`、`question_family_id`、`analysis_cluster_id`、answerability/reason、negative category、`citation_required`、`atomic_claims`、每 claim 的替代 evidence sets、`source/page/span/bbox/hash`、lineage，以及 generator/extractor/validator model、prompt、版本和 code 版本。所有校验、审计和失败记录可追溯。

## 5. Data Readiness（A）

定义并报告 accepted-file rate、accepted-page rate、ingest/build success、失败原因、idempotent duplicate 行为、build/rebuild time/cost、indexed file/chunk coverage（可观察时）、source/page provenance preservation、missing/duplicate evidence。

`ready` 只能表示 processed + embedded + searchable；UI 显示完成不构成 ready。替代 evidence set 中的 source files 必须 ready。产品失败是被测结果，不得用来删除 hard cases。

避免重复 `document-parsing` Track：RAG 只测 accepted file/page、searchable coverage、**Gold Evidence Preservation**（gold evidence 在 parsed/indexed/retrievable representation 中存活）、来源/页 provenance、缺失/重复证据。完整 OCR/layout/TEDS/formula 评分留在 document-parsing，可用于校准和 failure attribution，不作为 RAG 重复分数。

表格只能作为视觉/检索证据；SQL 执行、structured fusion 与 NL2SQL 属于 NLP2SQL，排除在本计划之外。

## 6. Evidence Retrieval & Scope（B）

有真实 retrieved traces 与 ranks/qrels 时才计算 `Document/Evidence Recall@K`、Complete Evidence-set Recall、Context Precision、MRR、nDCG、utilization 等；无 trace 明确写 `observability gap`，不得从最终答案反推检索结论。Citation 与 retrieval trace 分开保存。

题型覆盖 exact identifier、semantic paraphrase、distractor/version、multi-document 和单/多证据。选中文件 scope isolation 是核心：答案或 evidence 来自排除文件均为 violation。MOI 可额外做 disabled-chunk exclusion 的确定性验证；不把该 MOI 特性伪装为跨产品指标。

## 7. Native Answer & Citation（C）

adapter 保存 raw response，并规范化为 `response_claims[]`：`claim_id`、text、type、equal weight（除非预注册 criticality rubric）、support label、supporting evidence IDs、citation IDs。核心指标为 Correctness、Reference-claim Recall（不是 TRACe completeness）、Gold-evidence Support、runtime-context Faithfulness（仅诊断）、Citation Precision/Claim Coverage、unanswerable success、false refusal。

本节引用规范表中的 Gold-evidence Support、Citation Precision 和 Required Claim Citation Coverage；answerable 空答案或直接拒答的 Gold support=0。Citation-required answerable 题须同时满足 Precision=1 和 Coverage=1；对这类题，任何伪造或越 scope 引用均使 TDAS=0。无引用能力显式报告 `citation_capability=false`，不让 N/A 获得优势。

## 8. Fairness、配置与运行合同

每个 system manifest 冻结 exact product/deployment/frontend/backend/version/date/tenant/region/entitlements、cloud/private mode、resource/quotas/pricing，以及可观察的 parser/chunker/embedding/retriever/reranker/prompt/LLM。记录不可观察的 hidden defaults。所有系统使用同一 raw corpus/questions/time window、语义等价 instruction、fresh session、固定顺序轮换和等额 vendor help budget。

每题三次隔离重复，每次只有一个 scored initial attempt；实际 product/API failure 是有效零分。最多两次 retry 仅作 final-availability 诊断，记录时延/成本，不替换 initial score。`question_invalid` 仅限预注册 Gold/dataset defect，对所有 systems、conditions、repeats 全局排除但保留原记录；`run_invalid` 仅限单次 benchmark-side fault（请求未发出、adapter 崩溃、基准网络/写入故障），可按 replacement 规则处理，产品/API failure 不可 invalid。`batch_id` 定义为同一 `system_id × native_condition × frozen question set × repeat round/time window` 的运行批次；同一 batch 超过一次 benchmark-side fault 时，不把任何产品结果计零，整 batch 标记 `benchmark_execution_failure`，停止、修复、重冻结并整体重跑。replacement 使用新 run_id、`replaces_run_id`，任何排除须在看分前由盲 approver 签字，禁止看分后选择。保存 response、claims、citations、retrieved context/ranks/source map、timestamps、status/artifacts、cost/error/hash。

## 9. 人类、Judge 与统计

保留 blinded frozen primary judge，冻结 model/version/prompt/temperature/max output；至少 30-answer calibration，按 answerability、题型、系统和 score strata 分层，覆盖 MOI、Dify、FastGPT 三系统。两名 reviewer + adjudication，quadratic weighted kappa ≥ 0.60，kappa 对象为 claim-level correctness/support ordinal labels。固定人工 audit 配额为 `max(40, 20% of distinct hidden formal questions)`；抽样 unit 为 distinct hidden formal question，每个入样 question 覆盖所有 systems × native conditions 的同一预注册 repeat_id（按 question 轮换）。争议可扩展至该题全部 repeats，且不挤占固定配额。Gold validity 分母为抽审 Gold evidence sets/claims 总数，须 ≥95%，critical error=0；失败 strata 全审或重建。

先对每个 `system_id × native_condition × question_id` 的三次 initial repeat 固定取平均，再按 question 宏平均。bootstrap 以唯一 `analysis_cluster_id` 为抽样单位；每次 paired resample 同时抽取所有系统/conditions 下同一 question-level values，重新计算宏平均及 paired differences，10,000 次并报告 95% CI。bootstrap 不保留 raw repeats；run-to-run variance 另作描述统计，不混入主 CI。E 层因 human/operator confounding 只报告 runbook 原始证据和描述统计。

## 10. MOI Capability Validation（独立于横向比较）

单独验证 workflow topology/config export、parser artifacts/previews、page mapping、embedded-file eligibility/disabled chunks、selected-file scope、job status/retry/lineage/export。若其他产品存在共同等价能力，可移入 Common layer；不支持 export 必须显式披露，N/A 不得带来优势。

## 11. 门禁、执行与退出条件

| Gate | 退出条件 |
|---|---|
| identity/deployment/entitlements | 身份确认、版本/租户/区域/权限签名；Native Explore/API automation 与 trace-export 能力在 Smoke 前确认 |
| corpus/security/fresh-control | manifest/hash/授权/egress 通过；fresh slice 与题目就绪 |
| native path + automation/observability smoke | 三产品 Native journey 可运行，关键状态/artifact/错误可保存 |
| data readiness/artifact contract | ready criterion、Gold preservation、provenance 与失败字段可校验 |
| dataset/judge | schema、配额、20/80 split、calibration/kappa、Gold audit 通过 |
| Quick-start freeze/run | 默认配置、支持预算、三次初始尝试和 raw records 完整 |
| optimized freeze/run | bounded dev budget、配置签名、三次初始尝试完整 |
| blind audit/report | CI、缺失能力、失败归因、限制与审批清单齐全 |

Gate 失败停止正式扩展；修复后重冻结受影响配置/数据。invalid-run 保留原 run_id/hash 和原因，严禁静默删除、选择性重跑或用 retry 修复主分数。

## 12. 失败分类与报告

Failure taxonomy 连接 `ingest → parse/artifact → embed/index → scope/retrieval → generation/citation → platform/API`，每个失败保留证据、时间和责任边界。

报告必须分开：Common Product Scorecard（跨产品 component metrics/TDAS 分层）、Stage Diagnostics（仅 observable）、Quick-start 与 Optimized、public_baseline 与 fresh-control、MOI Capability Validation、失败分类、限制与缺失能力。不得发布单一 winner。

## 14. 延后项目与风险

延后/另轨：MOI→Dify、DeerFlow/MCP integrations、agent actions、NL2SQL/table execution、GraphRAG、audio/video/image-only、multi-turn、RBAC/multitenant security/poisoning、dynamic freshness、high concurrency/HA/elasticity/cost-at-scale。它们是 roadmap，不代表不重要或无关。

主要风险及缓解：PDF/产品解析不对等则保留 hard cases 并归因；版本/近重复泄漏则 family connected-component split；egress/敏感数据走 security gate；Judge 偏差由盲化、双 reviewer、kappa 和 Gold audit 控制；无 trace 标 observability gap；参数记忆由 fresh-control、版本精确和 citation/unanswerable 题缓解；重试掩盖不稳定由 initial-first 规则缓解；窄域英文硬件语料限制外推。

## 修订摘要

v0.3 supersedes v0.2：由“答案中心”的 RAG 评测改为产品级 benchmark，将数据就绪、证据/范围、Native 答案与引用、可靠性/性能、产品可运维性纳入同一 native journey；以 TDAS 取代模型准确率或综合冠军；引入 fresh-control、MOI 身份/能力独立验证、Quick-start/Optimized 双条件、严格 trace 可见性与仓库治理。v0.2 的证据优先 schema、claim 指标、盲 Judge、三次初始尝试、invalid-run 与 cluster bootstrap 规则均被保留并扩展。
