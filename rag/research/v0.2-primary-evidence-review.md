# RAG Benchmark v0.2：一手证据复核

> 复核范围：只判断会直接改变当前“同一批原始 PDF、各产品原生建库、单轮端到端问答”方案的外部主张。`rag/refs/` 仅用作线索；以下结论来自正式论文、作者仓库或官方数据页。

## 决策摘要

1. **主榜继续使用自建、冻结的原始文件与隐藏问题。**公开 benchmark 可用于借鉴指标、校验 evaluator，或另设补充轨道；不能把其分数与本项目的原生 PDF 建库结果混成一个总分。
2. **主结果拆成四个不可互相替代的维度：**参考答案正确/完整、对实际证据的忠实度、引用质量、可回答性/拒答；检索指标仅在产品能导出真实召回上下文时报告。
3. **首版优先采用“规则 + claim-level 固定 Judge + 盲化人工校准”。**RAGAS 可做快速基线，RAGChecker 可做有 trace 样本的细粒度诊断；ARES 不适合作为零标注的默认方案。
4. **不支持“完全不需要人工校准”。**RAGBench 本身用人工子集校验自动标签；ARES 的 PPI 路线明确需要人类标注。正式发布前应对分层抽样样本做匿名人工复核，并报告 Judge 与人工的一致性。

## 直接适用的证据

### 1. RAGBench / TRACe：采用分解思路，不直接照搬分数

[RAGBench 论文](https://arxiv.org/html/2407.11005)把 TRACe 定义为：

- **Relevance**：召回上下文中与问题相关的比例；
- **Utilization**：召回上下文中被回答实际使用的比例；
- **Completeness**：相关上下文中被回答使用的比例；
- **Adherence**：回答是否全部受上下文支持，即 faithfulness/groundedness。

这套分解能区分“召回噪声”“召回到了但未使用”“遗漏相关证据”“无依据生成”，适合本项目的失败归因。需要特别修正命名：**TRACe Completeness 不是“参考答案要点覆盖率”**。计划中后者应命名为 `Reference-claim Recall / Answer Completeness`，两者不能混用。

局限也很直接：RAGBench 把 12 个既有数据集转换成固定 `question + documents + response` 形式，回答主要由 GPT-3.5/Claude 生成，标签由 GPT-4 生成；Relevance/Utilization 的细粒度人工核验只覆盖一个很小的子集。它主要检验 evaluator，而非从原始文件解析、切分、索引开始的产品原生管线。因此：

- 有真实召回 trace 时，可计算 context relevance、claim/evidence recall、utilization 等诊断项；
- 无 trace 时只评端到端回答和产品可见引用，不能从最终答案反推召回；
- 不能把某个通用 LLM Judge 当作真值。论文只证明其特定微调 DeBERTa 在该任务上优于所测 few-shot Judge，不能泛化成“小模型总是优于 LLM Judge”。

[官方 RAGBench 数据页](https://huggingface.co/datasets/galileo-ai/ragbench)标注为 CC BY 4.0，可作为 evaluator 回归集；但其 processed contexts 不是原始 PDF，因此不进入本项目主榜。

### 2. RAGAS、RAGChecker、ARES：用途和前提不同

- [RAGAS（EACL 2024）](https://aclanthology.org/2024.eacl-demo.16/)提供 reference-free 的 context relevance、faithfulness、answer relevance 等自动指标，适合快速回归和第二意见。其分数依赖 Judge、Embedding、Prompt 和版本，故只能在冻结配置并经人工样本校准后使用，不能单独决定产品排名。
- [RAGChecker（NeurIPS 2024）](https://proceedings.neurips.cc/paper_files/paper/2024/hash/27245589131d17368cccdfa990cbf16e-Abstract-Datasets_and_Benchmarks_Track.html)以 claim-level 检查同时诊断检索和生成；[官方仓库](https://github.com/amazon-science/RAGChecker)明确说明每题唯一必需的标注是 ground-truth answer，**不要求预先标注 Gold Context**。但检索、faithfulness、context utilization 等诊断仍需要产品实际 `retrieved_context`。因此它适合“能导出 trace 的产品子集”，不能成为所有产品共同主指标。
- [ARES（NAACL 2024）](https://aclanthology.org/2024.naacl-long.20/)通过领域合成数据训练轻量 Judge，再用 prediction-powered inference 校准并给出置信区间。论文流程需要领域语料、少量 in-domain 示例，以及至少约 150 条人类偏好标注。它适合后续有稳定标注预算的 evaluator 工程，不是首版“无需人工标注”的即插即用首选。

**推荐落地：**以参考答案的原子 claim 计算 correctness/completeness；以产品实际上下文或引用证据计算 claim support/faithfulness；RAGAS 只作对照，RAGChecker 只作可观测样本的诊断，任何单一 Judge 都不直接生成唯一总排名。

### 3. Citation 与 faithfulness 必须分开

[ALCE（EMNLP 2023）](https://aclanthology.org/2023.emnlp-main.398/)要求系统端到端检索证据并生成带引用回答，把 fluency、correctness、citation quality 分开；[作者仓库](https://github.com/princeton-nlp/ALCE)实现了 citation recall 与 citation precision。其含义适合本项目：

- `Citation Recall`：需要证据的回答 claim 中，有正确引用支持的比例；
- `Citation Precision`：给出的引用中，确实支持所关联 claim 的比例。

ALCE 同时指出自动 NLI 对“部分支持”判断有限。因此 Gold 应保存 `atomic_claim -> source_file -> page/section -> evidence span`，Judge 必须先拆 claim、再判证据支持，重要样本抽查。Faithfulness 评价回答是否受上下文支持；citation 评价用户看到的具体来源是否支持相应 claim，两者不能互相替代。

产品没有引用能力时应明确报告 `citation_capability=false`。若“可审计引用”是主轨道硬要求，则无引用的 claim 计入 citation recall 的漏项；若不是硬要求，则另设 Citation Track，不能只给支持引用的产品报分而让其余产品显示为无惩罚的 N/A。

### 4. 拒答：同时衡量正确拒答和错误拒答

[RGB（AAAI 2024）](https://ojs.aaai.org/index.php/AAAI/article/view/29728)把 noise robustness、negative rejection、information integration、counterfactual robustness 分成四个 testbed；其中 negative rejection 专门测试只有相关噪声、没有充分答案时是否拒答。这支持在隐藏集中纳入无答案题，但**只报“拒答率”会奖励永远拒答的系统**。

每个产品至少同时报告：

- 无答案题正确拒答率，以及编造/错误引用率；
- 可回答题错误拒答率；
- answerable 与 unanswerable 分层的任务成功率。

无答案题应包含“完全不相关”和“主题相近但缺少关键事实”的近失配证据；不得只把随机外域问题当作拒答测试。RGB 是给定检索文档的生成能力测试，不包含原始 PDF 建库，因此只借用能力定义，不复用其分数。

## 公开 benchmark 的复用边界

可接受的复用方式：

- 用 RAGBench 的人工/自动标签数据校验候选 Judge 的方向性；
- 单独建立一个公开、文本化的补充轨道，以检验结论是否只对内部语料成立；
- 借用 ALCE 的 citation protocol、RGB 的 negative-rejection 构造方式和 RAGChecker 的 claim-level 诊断。

不可接受的方式：

- 把 RAGBench 的固定 contexts 当作“原生 PDF 端到端”结果；
- 把 BEIR/MTEB 等 retrieval-only 排名解释为产品最终问答质量；
- 把来自不同语料、不同 Judge、不同检索开放性的公开分数与本项目主榜做加权总分；
- 未逐项检查数据许可、原始文档可再分发性和测试污染风险就把公开集复制进正式发布包。

## 从 `rag/refs/` 明确延后或拒绝的项目

- **Agentic web、实时新闻、浏览轨迹、模型路由成本**：当前是固定知识库单轮问答，检索介质和交互协议不同；留到独立 Agentic/Dynamic Track。
- **GraphRAG 投毒、RBAC/多租户权限、安全攻击**：重要但不是当前产品主榜的构念；不能用几个新预印本扩张首版范围。
- **多轮对话 benchmark**：当前样本没有会话状态 contract，贸然加入会混淆 query rewrite、memory 与知识库能力。
- **2025–2026 新多模态/文档 benchmark**：可在图表、图片、版式题成为稳定独立子集后再复核；首版先用自有 PDF 的页级证据和明确可答题验证真实产品解析能力。
- **“某框架可解决企业评测 60%–80%”“某方法是行业唯一首选”“公开 benchmark 能代表真实企业部署”等数字或强结论**：所查一手来源没有支持，v0.2 不应采用。

## 对 v0.2 的最小修改建议

1. Golden schema 增加 `reference_claims[]`、每个 claim 的 `evidence_spans[]`、`answerable_reason`、`citation_required`，并区分产品 `retrieved_contexts` 与用户可见 `citations`。
2. 主表报告 Answer Correctness、Reference-claim Recall、Claim Faithfulness、Answerable/Unanswerable Task Success；Citation Precision/Recall 依据预先声明的 Citation Track 规则报告。
3. Context/Recall/Utilization 只作为 trace 可用时的诊断表，不参与所有产品共有总分。
4. 冻结 evaluator 模型、版本、Prompt、解析器和重试策略；用盲化、分层人工样本校准，并保存逐 claim 判定与证据，允许复核。
5. 公共数据只进入 evaluator validation 或单列 supplemental track；主榜始终从同一批冻结原始文件开始。
